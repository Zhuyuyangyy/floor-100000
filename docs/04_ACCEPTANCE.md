# ACCEPTANCE — 可玩性与自动化验收

## A. 基础技术门槛

- [ ] 从干净仓库安装依赖，可执行 `npm run dev` 并打开浏览器。
- [ ] `npm run typecheck` 无错误。
- [ ] `npm run test` 全通过，失败测试不能用 `skip` 掩盖。
- [ ] `npm run build` 成功并能打开构建预览。
- [ ] `npm run test:e2e` 实际以 Chromium 执行，不是伪造结果。
- [ ] Canvas 有像素内容，状态面板、角色与当前楼层数字可见。
- [ ] 浏览器控制台无未处理异常、资源 404 或持续报错。

## B. 关键玩法门槛

- [ ] 开局生命/饥渴/精力和初始物资精确对应配置。
- [ ] A/D 移动，E 可交互，楼层上下切换且不会越界。
- [ ] 物品拾取、背包堆叠、满包提示、物品使用正确。
- [ ] 核心生存数值随游戏时间下降；使用资源有反馈。
- [ ] 回家、制作、睡眠、日期变化可真实发生。
- [ ] NPC 对话与交易能改变真实状态。
- [ ] 随机事件可复现，威胁有可行规避方式。
- [ ] 生命归零出现失败画面；第 8 天 06:00 胜利画面。
- [ ] 通关不依赖 Debug 命令、直接改存档或跳过天数。

## C. 数据持久性和一致性

- [ ] 搜刮过的容器刷新或重载后不会重置成未搜刮。
- [ ] 制作、交易、数值变化保存前后无丢失或重复扣除。
- [ ] 同 seed、同操作序列下，关键事件/掉落可复现。
- [ ] 损坏存档提示清楚并可开始新游戏。
- [ ] 恢复存档后没有幽灵 NPC、重复角色、冲突物品。

## D. 真正的人工试玩门槛（自动化不能代替）

- [ ] 新用户 30 秒内知道怎样开始/移动。
- [ ] 新用户 3 分钟内找到资源并实际用掉一种道具。
- [ ] 第一日要有实质的生存决策，不是等血条慢慢掉。
- [ ] 死亡原因可解释，不是无预警被随机事件秒杀。
- [ ] 开局 2 天内有足够且可信的生存资源，不产生必死局。
- [ ] 连玩 15 分钟后仍有事情可做；如没有，要优先修玩法，不扩楼层。

## E. 自动化执行证据模板

对每个任务提交/PR，记录：

1. TASK ID 与改动摘要。
2. `typecheck`、`test`、`build`、`e2e` 的执行命令和真实结果（失败附错误摘要）。
3. 关键行为的输入、前置状态、输出状态或短录像/截图。
4. 浏览器截图路径与分辨率；说明有没有肉眼复核。
5. 未完成项与已知 bug；绝不以“理论上可运行”代替验证。

## F. 自动 QA Seeds

固定覆盖 `1`、`42`、`2026`。可使用 `?seed=<n>` 开启同种子测试。仅测试 fixture/开发构建可以注入特定 GameState，正式运行不能依赖此机制。
