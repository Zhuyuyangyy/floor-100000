# B3-12 移动手感：从阶跃到斜坡

负责人反馈「这个移动怎么这么生硬」。本文件记录诊断、实现与实测。

## 1. 诊断：四个原因，其中一个我一开始说错了

| # | 判断 | 核实方式 | 结论 |
|---|---|---|---|
| 1 | 角色从不转身，向左走是倒着滑 | 逐色 ASCII 图 + 镜像不对称度 + 肤色质心 | **错，已撤回**。四个角色全是正面朝向，`flipX` 只会把挎包从一侧甩到另一侧 |
| 2 | 没有任何动画 | `grep anims.create` 全 `src/` 零命中 | 成立。玩家是一张静态 64×96 图，走路 = 整图平移 |
| 3 | 速度阶跃 | [GameScene.ts:1250](../src/scenes/GameScene.ts) 旧代码 `dir * PLAYER_SPEED` | 成立。按下即满速、松开即归零 |
| 4 | 静止时完全静止 | 无待机起伏 | 成立 |

### 关于「转向」的更正

我最初告诉负责人：按左键人物面朝右倒退着走，一行 `setFlipX` 就能修。**这是错的。**

用三个独立方法核实：

1. **逐色 ASCII 图**（每个不同色用一个字符，不是透明/不透明两字符——后者按构造不可能显示轮廓内部）：人物正面站立，脸在画面水平中心。
2. **镜像不对称度**：四个角色 30.2 / 33.4 / 35.5 / 46.3，都不对称——但不对称来自挎包、口袋、肩带等**非对称配件**，不是朝向。
3. **肤色质心**：`char-xiaozhou.png` 最亮像素在 (32, 15)，即 64×96 画布的正中心。

结论：正面朝向的美术没有「转身」可做。真实转向需要侧面行走帧，那要负责人供素材。

## 2. 实现

三个纯函数放进 `src/systems/FloorSystem.ts`（与 `movePlayerX` 同属「纯移动规则」），常量进 `src/core/constants.ts`：

| 函数 | 作用 |
|---|---|
| `stepHorizontalSpeed(current, dir, deltaMs)` | 速度斜坡。加速 900 px/s²，减速/转向 1500 px/s² |
| `advanceBobPhase(phase, speed, deltaMs)` | 走路周期相位，**按行进距离推进**而非墙钟时间 |
| `bobOffsetPx(phase, speed)` | 垂直抬升，按速度缩放 |

关键设计：

- **减速快于加速**：掉头用刹车率而非加速率，转身才像踩了一脚而不是溜冰。
- **减速不跨零**：`Math.max(0, …)` / `Math.min(0, …)`。这是长帧（切后台再回来）不会把人甩到反方向的原因。
- **bob 按距离推进**：加速过程中脚不打滑，与自己的步子保持同步。
- **`scale === 0` 时短路返回 0**：`Math.sin(3π/2) * 0` 是 `-0`，而契约是「站立时脚在地面线上」。这是测试先红、实现在实现里显式保证、而不是放宽断言的例子。

### 场景侧

`speedX` / `bobPhase` 两个字段在 `clearFloor()` 里归零——Phaser 的场景重跑 `create()` 但**不重跑类字段初始化器**，不清零就会以满速或相位中途恢复。

相机纵向被 `setBounds(0, 0, 1280, 360)` 锁死（视口高 360，可滚动范围 0），所以 bob 永远不会和跟随相机打架，2px 全额可见。

## 3. 实测（浏览器内定步长驱动循环，逐帧记录）

由于本机 Browser 面板画布上屏只有 ~1.2fps（见 §5），改用**手动定步长调用 `scene.update(0, 16.667)`** 逐帧采样，结果确定、可复现：

```
加速：15 30 45 60 75 90 105 120 130 130 …     每帧 +15 = 900 px/s²
减速：105 80 55 30 5 0 0 0 …                 每帧 −25 = 1500 px/s²
bob ：y ∈ [318.002, 322]，基准 320            ±2px
周期：15 帧/周期                               ≈4Hz
停稳：y 精确回到 320，v 精确为 0
100 帧行进 214.5px（均速 ~128 px/s）
```

### 「重量感」来自哪里

同样时长的按键，新旧覆盖距离对比（旧 = 阶跃 `130 * 秒数`）：

| 按键时长 | 旧 | 新 | 差异 |
|---|---|---|---|
| 17ms | 2.17 px | 0.25 px | −88% |
| 50ms | 6.50 px | 1.83 px | −72% |
| 83ms | 10.83 px | 5.00 px | −54% |
| 167ms | 21.67 px | 17.92 px | −17% |
| 333ms | 43.33 px | 39.58 px | −9% |
| 1s | 130 px | 126.25 px | −3% |

短按明显变短，长跑几乎不变——斜坡只吃掉加速那一段，横穿楼层的总距离不受影响（126 vs 130，差的 3% 就是斜坡本身）。

### 一处中途更正

第一版 `PLAYER_BOB_CYCLES_PER_SECOND = 7.5`，我读实测数据时把周期看成了 16 帧，实际是 **8 帧**（峰值在 f=9, 17, 25, 33…）。结论不变——8 帧一周期是震颤不是走路——但数字写错过一次，已在常量注释里改正。

改为按**步幅**表达而非频率：`PLAYER_BOB_STRIDE_PX = 32`。用 Hz 表达时，一旦 `PLAYER_SPEED` 被重新调参，这个数字的含义会静默改变。并加了 `cadence in walk range` 测试，把周期锁在 10–25 帧。

## 5. 发现的环境问题（非本轮引入，未修）

**游戏在 Browser 面板里以约 1.2–2.8 fps 运行。** 定位过程：

| 实验 | 结果 | 结论 |
|---|---|---|
| 循环运行时 rAF | 1.1 fps | — |
| `g.loop.sleep()` 后 rAF | **60 fps** | 成本在循环内 |
| `canvas { display: none }` 后 rAF | **60 fps** | 成本在画布上屏，**不在逻辑** |
| Menu 场景单独运行 | 2.8 fps | 与 GameScene 改动无关 |
| WebGL renderer | ANGLE / AMD Radeon 780M / D3D11 | 不是软件渲染回退 |

即：逻辑跑满 60fps，只有合成/上屏慢。这也是本轮改用定步长驱动做验证的原因。**真实手感需要在正常帧率下人工确认**，这一步我没做到。
