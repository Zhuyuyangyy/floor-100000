## 0. 一句话结论

**当前 UI 的工程完成度远高于它的产品完成度。**

配色、字族、面板框架、格子网格都已经是一套能用的系统；但有几处
「玩家实际会卡住」的缺陷，全部来自同一个根因：**布局数值是按「代码里写着舒服」
定的，没有按「眼睛看上去对不对」校过一遍**。

三条最刺眼的（**截至 2026-11-26 晚，第 1 条已修，第 2、3 条待修**）：

1. ~~**角色选择的说明文字，被自己面板的底部按钮压掉了一半，并且整行溢出面板左边界。**~~
   **已修**。根因是中文 `wordWrap` 在这个项目里**从来没生效过**（没开 `useAdvancedWrap`，
   中文没有空格，整句被当成一个不可断的词）。修法不是调字号，是把说明搬出按钮带、
   给足折行宽度、再开 `useAdvancedWrap`。同一个根因在背包详情里还留了一处未修
   （`invDetailBody`，实测跑出面板 238px，见 B-2 #8b）。
2. **世界层的家具标签会被顶部 HUD 带切掉。** 实测 `储物柜` 标签在屏幕 y=121–144，
   而 HUD 不透明带的底边在 y=124。也就是说标签上沿有 3px 永远压在 HUD 底下。
3. **竖屏（手机）的 HUD 把四宫格挤成两列 195px，数值贴在格线上，「100」的最后一个 0
   压住了右边那个格子的边框。**

## 2. 阻断级问题（玩家看不懂 / 点不到）

### B-1 角色选择：说明文字溢出面板左边界，并被「开始生存」按钮遮住 `[阻断]`

**现象（实测像素）**

以下全部是 `e2e-audit/meta-geom-probe.spec.ts` 打印的 `getBounds()` 实测值
（画布坐标；横屏 1280x800 视口下 1 画布像素 = 1 屏幕像素）：

```
说明文字 bbox      x[287..647] y[450..469]   360x19
面板填充 bbox      x[405..875] y[210..511]   470x300
「开始生存」按钮   x[553..713] y[454..490]   160x36
```

- 文字左沿 287，面板左沿 405 → **向左溢出 118px**，跑出面板、压在外面的
  宿舍背景上。
- 文字右沿 647 < 面板右沿 875，所以**不是右侧溢出**，只在左边。
- 文字 y[450..469] 与按钮 y[454..490] 相交 → 交叠区 **94 × 15 px**；
  也就是文字从 x=553 起的「只有背包。」整段被半透明绿按钮盖住。

**根因（精确到常量）**

`src/scenes/MetaSelectScene.ts`，`this.flavourText = this.add.text(...)`（约 :107）

```ts
this.add.text(portraitX, portraitFeet + 10, '', {
  fontSize: mobile ? '12px' : '18px',
  wordWrap: { width: mobile ? 82 : 132 },   // ← 中文不折行
}).setOrigin(0.5, 0)

两个错误叠加：

1. `portraitX` 的 `origin` 是 `(0.5, 0)`（居中锚点），但 `wordWrap.width = 132`。
   Phaser 的 `wordWrap` **只在文本宽度超过 wrap 宽度时**才折行；中文没有空格，
   而且**当时这个项目所有 Text 都没开 `useAdvancedWrap`**（写作时全仓 0 处），
   所以整句被视作一个词，**根本不折行**，直接左右各溢出半个宽度。
   （现在已有 3 处开了 advanced，见 B-2 的口径说明。）
2. 按钮 `startY = top + panelH - 38`，说明文字 `y = portraitFeet + 10`，
   在桌面分辨率下两个 y 相差不到 10px，且按钮在 depth+7、文字也在 depth+7，
   后创建者胜出 → 按钮盖住文字。

`e2e-audit/wrap-probe.spec.ts` 的实测输出：

```
[wrap] "从底层醒来的那个人。没有特长，只有背包。" size=18px width=360.0 wrap=132 height=19.0 advanced=false >>> OVERFLOWS WRAP BOX
[wrap] "标准规则。自动存档，死了就重来。"           size=18px width=288.0 wrap=150 height=19.0 advanced=false >>> OVERFLOWS WRAP BOX
```

**评委看到会怎么想**：说明文字跑出面板、还被按钮压掉后半句，
这是「demo 前没打开过这个界面」的信号——评委通常只给 3 分钟，第一屏的破版就是全部印象。

**改法（三选一，建议 1+3 组合）**

1. **给这两处 Text 加 `useAdvancedWrap: true`**
   `{ wordWrap: { width: 132, useAdvancedWrap: true } }`
   中文按字断行，宽度立刻守住。
2. 说明文字改成左对齐 `setOrigin(0, 0)`，x 取 `left + 12`（= 417），宽度 `listW - 24`，
   与上面的角色列表左边缘对齐（现在它 `setOrigin(0.5,0)` 居中锚在 `portraitX`，
   中心落在 467，于是 360 宽的文本向两边各甩出 180，左边直接出框）。
3. 把说明文字移出「立绘下方」这个位置——它现在和按钮抢同一块 y 空间。
   按钮在 `const startY = top + panelH - (mobile ? 45 : 38)`（约 :220），
   说明文字在 `portraitFeet + 10`，两者相差不到 10px，且同在 `depth + 7`，
   后创建的按钮胜出。建议说明文字放面板底部单独一行，按钮上移。

**附带**：`标准规则。自动存档，死了就重来。`（模式说明）有同样问题，
它在 `MetaSelectScene.ts` 的 `MODE_BLURBS[meta.mode]` 那个 text（约 :175），
`wordWrap: { width: mobile ? panelW - 32 : 150 }`，实测宽 288px。

### B-2 中文换行全局失效（不是个案） `[阻断]`

上一条不是孤例，是**整个项目的布局隐患**。现状口径（2026-11-26 复核，别和别的数字混用）：

```
grep -rn "wordWrap" src/ --include="*.ts" | grep -v test     → 15 处（含 1 行注释）
实际调用点                                                    → 14 处
useAdvancedWrap: true                                        → 3 处
  ├ GameScene.ts:3391  dialogueMessage（team-lead 的 bac96ae）
  ├ MetaSelectScene.ts:152  角色说明（本轮 B-1 修复）
  └ MetaSelectScene.ts:220  模式说明（本轮 B-1 修复，顺手）
```

**根因比「忘开开关」更底层**（这段是 team-lead 翻 Phaser 源码查出来的，记在这里防止有人改回去）：

`basicWordWrap` 的实现是 `text.split(' ')` 逐词累加。中文整句没有空格，
所以**整句是一个「词」**。而「词比整行宽」那条分支的守卫是 `if (j > 0)`——
只有前面已经累过至少一个词才成立。首词时 `j === 0`，守卫直接跳过，
于是零折行。`advancedWordWrap` 在首词超宽时走 `j === 0` 分支逐字裁切，
这才是中文能折的原因。

也就是说：**这不是「排版偏好」，是这个项目的文本能否折行的开关。**
14 处里任何一个被喂进超过 wrap 宽度的中文，都必然横向溢出。

### B-3 竖屏 HUD：四宫格数值压住格线，触屏按钮盖住底部提示 `[阻断]`

- `GameScene.ts` 的 `const buttonY = DESIGN_HEIGHT - 25;`（约 :2481）：固定值，未考虑提示文字占用

1. 数值右边界从 `- 4` 改为 `- 12`：右沿变成 152 / 306，距板右沿剩 8px，

2. 按钮行 `buttonY` 从 `DESIGN_HEIGHT - 25`（= 695）改为 `- 19`（= 701）会让

   竖屏分支的 y 从 `DESIGN_HEIGHT - HUD_FOOT_H - 14`（= 666，文本中心）

### M-1 世界层标签被 HUD 上下文带切掉 `[明显]`

**实测**（`hud-band-probe.spec.ts`，7 个玩家位置扫一遍）：

```
x=200: "储物柜"[121..144] inside HUD band (hudBottom=124)
... （7 个位置全部命中，共 7 次）
```

`储物柜` 标签的屏幕 y 是 121–144，HUD 不透明带底边 124，**上沿 3px 被切**。
放大图 `_zoom/f1-cab.png` 里能看到「储物柜」的最上面一笔正好压在 HUD 下边框上。

**根因**

- `GameScene.ts` `buildContainers()` 里的容器标签（约 :2261）：y = `y - 4 - box.displayHeight - 8`，其中 `y = FLOOR_HEIGHT - 64`
  用的是**世界坐标**（相对楼层底），`FLOOR_HEIGHT = 200`
- `hudLayout.ts:7`：`contextBottom = 124`（屏幕坐标，不透明带）
- 摄像机跟随玩家后，世界坐标 y 与屏幕坐标 y 不是固定偏移。当玩家站在楼层中段，
  标签就落到 121–144 这条带子里。

**评委看到会怎么想**：家具名被横条切掉上沿，会被读成「这个 demo 的分辨率没调好」，
而不是「HUD 和世界的层级需要收边」。

**注意**：这不是「标签画错了」，而是「标签会周期性滑进 HUD」——
玩家往右走，标签往左移也会改变屏幕位置，但**竖直方向**受摄像机上下跟随影响。
所以修法不是调标签的 y，而是：

**改法**

1. 把不透明 HUD 带改成**渐变收边**（底部 8px 从 `surface` 渐到透明），
   被切的部分会淡出而不是被硬切——成本最低，视觉上也更像「遮挡」而不是「切字」。
2. 或者给世界标签加 `setScrollFactor(0)` 并在 HUD 带以下裁剪（把标签改成
   「靠近时才出现的交互牌」），这符合用户想要的方向（见 §5 的 HUD 建议）。
3. **不推荐**简单把 HUD 带调矮：`contextBottom = 124` 是两条上下文行
   （目标 + 环境）的宿位，调矮会让这两行压在一起。

### M-2 背包：数量徽标压住图标，格子间隙 5px 破坏 4px 网格 `[明显]`

**现象**（`05-inventory.png`、`_zoom/inv-panel.png`）

`e2e-audit/panel-geom-probe.spec.ts` 实测（横屏）：

```
格子 12 个，4 列 x 3 行
格宽 40，步距 45  → 间隙 5px（不是 4 的倍数）
网格 bbox x[432..607] y[272..402]，末格右沿 607
徽标「3」 bbox x[456..469] y[286..309] 13x23
徽标右沿 469 vs 格右沿 472 → 距边只有 3px（setOrigin(1,1) + CELL-3）
```

- 徽标的 `strokeThickness: 3` 让它**实际占位比 bbox 大 3px 一圈**，所以
  描边外沿正好顶到格子边框内侧；放大图里「3」的白描边压在水瓶图标右下角，
  两个形状互相干扰。
- 间隙 5px 让 4 列总宽 175，与 `UI_UNIT = 4` 的网格不对齐。横向累积到第 4 格
  就差 3px，与右侧详情区的分界线之间会多出一条肉眼可见的窄缝。

**根因**

- `GameScene.ts` `buildInventoryPanel()`（约 :2738-2739）：
  `const CELL = this.portraitMode ? 32 : 40; const GAP = this.portraitMode ? 4 : 5;`
  —— 竖屏已经用 4，横屏还用 5，两套不一致。
- `GameScene.ts`（约 :2761）：徽标 `x + CELL - 3, y + CELL - 3`，`strokeThickness: 3`

**评委看到会怎么想**：背包是评委唯一会主动点开的界面（想知道能捡什么）。
数字描边压在图标上会被读成「素材质量低」，而其实是排版；两者在评委那里没有区别。

**改法**

1. `GAP` 从 5 改 4 → 步距 44，四列 172；或者 6 → 步距 46，四列 178。二者都
   比 175 干净。推荐 **4**（保持 4px 网格）。
2. 徽标从「右下角贴边」改为「右下角内缩 4px」：`x + CELL - 4, y + CELL - 4`，
   并且把描边从 3 降到 2（16px 图标原生只有 16px 宽，3px 描边太重）。
3. 更好的方案：徽标加**深色胶囊底**（`backgroundColor: '#0b0f12dd'`，padding 1–2），
   这样图标复杂时数字仍然可读——现在的白描边在深色图标上会消失。

- `行商` 在 `PLAYER_FEET_Y - 108`，货架名（`邻居货架（空）`）在容器标签位置
  `FLOOR_HEIGHT - 64 - height - 8`，两者在同一竖直列上，**行商标签的正下方**
  就是货架名，视觉上像一个两行的招牌。
- 四位居民的名字各有深色底，间距 `INTERACT_DISTANCE=44` 内不会重叠，
  但第 2 层放了 4 个 NPC + 1 个行商 + 2 个问号点，**同一屏 7 个标注**，
  名字底板的密度已经接近临界。

**根因**

- `GameScene.ts`（约 :959）：行商标签 `shopX, PLAYER_FEET_Y - 108`，字号 22，色 `TEXT.highlight`
- `GameScene.ts` 的 `buildContainers()`：容器标签贴在道具上方，字号 22，**无底色**
- `data/npcs.ts`：第 2 层 `x = 320 / 480 / 800 / 960`，加行商

**评委看到会怎么想**：一屏 7 个标注会把「末日宿舍」读成「一个有很多标签的房间」，
气氛全部被说明文字吃掉。

**改法**

1. 行商标签从「行商」改为带上身份的两段式，或者干脆并入 NPC 标签体系

   前者是青色后者是米白，玩家会以为行商是另一种东西）。
2. 容器标签在被玩家靠近之前**不显示**（见 §5 第 6 条），能同时解决 M-1 与 M-4。

### M-5 夜幕：只有压暗，没有色温；且 18:00 就开始「夜」`[明显]`

**实测**（`night-probe.spec.ts`）：

```
06:30 → alpha 0
12:00 → alpha 0
18:00 → alpha 0.6   ← 傍晚就已经是全黑
21:00 → alpha 0.6
02:00 → alpha 0.6
```

- `NIGHT_START_MINUTE = 1080` = **18:00**，一个阶跃：17:59 白天，18:00 全黑。
- 遮罩颜色 `0x05070a`（近乎纯黑），所以「夜晚」= 把画面整体乘 0.4。
  逐像素实测（采样窗口 = 世界区 `y ∈ [180,640)`、`x ∈ [10, w-10)`，步长 2，
  避开 HUD 与底栏；两张图同一层同一窗口）：

  ```
  04-floor-2-residents-mid.png（白天）  平均亮度 43.5
  10-night-floor-2.png       （20:30）  平均亮度 37.8   → 只降 13.1%
  03-floor-1-boot.png        （白天）  平均亮度 44.5   → 与 04 同量级，说明窗口稳定
  ```

  也就是说 alpha 0.6 的黑色遮罩，在这样一个本来就已经很暗的场景里**只压下去 13%**。
  玩家几乎看不出「天黑了」。
- 更关键的：**没有任何色温变化**。夜晚和白天是同一个冷灰，只是暗一点，
  所以「昼夜」在体感上不存在，只有 HUD 的 `D1 20:30` 在告诉你现在是晚上。

**根因**

- `SurvivalSystem.ts:195`：`NIGHT_START_MINUTE = 1080`（硬阶跃）
- `CraftingSystem.ts:97`：`DARK_NIGHT_ALPHA = 0.6`
- `GameScene.ts`：夜幕 `.setFillStyle(0x05070a, 1)`（约 :578，`setName('night-overlay')`）—— 中性黑，无蓝移

**评委看到会怎么想**：这是**最影响「氛围类奖项」评分**的一条。
评委看的是「昼夜有没有说服力」；只有压暗没有色温，等于把昼夜做成了一个亮度滑条。

**改法（低成本、高体感）**

1. 遮罩颜色从 `0x05070a` 改成**冷蓝**，例如 `0x0a1220`（蓝通道 > 红通道）。
   同样是 0.6 alpha，画面会从「变暗」变成「变蓝」，昼夜立刻可感。
2. 把阶跃改成 **18:00–20:00 线性爬升**，alpha 从 0 → 0.6。`night-overlay-alpha`
   是个纯函数（`nightOverlayAlpha(state)`），加一段 `lerp` 即可，无副作用。
3. 04:00–06:00 反向衰减（黎明）。同样一个 lerp。

这三条加起来约 20 行，是全项目**性价比最高的氛围改动**。

### M-6 危重状态：只有一条属性变红，另外三条低的没有视觉区别 `[明显]`

**现象**（`11-critical-hud.png`：HP 14 / 饥饿 8 / 口渴 5 / 精力 22）

- 四条属性里三条都在危险区间（14 / 8 / 5 / 22，满值都是 100），但**只有
  占比最低的那一条**（`mostUrgentStat`）标签与数值变色。
  逐格取色实测（`11-critical-hud.png`，取每格标签区与数值区的最亮像素）：

  ```
  第0格 生命 14  标签 #a8a49a(灰)   数值 #ece8d8(米白)
  第1格 饥饿  8  标签 #a8a49a(灰)   数值 #ece8d8(米白)
  第2格 口渴  5  标签 #e8907c(警告) 数值 #e8907c(警告)  ← 唯一变色
  第3格 精力 22  标签 #a8a49a(灰)   数值 #ece8d8(米白)
  ```

  也就是**生命只剩 14 / 100（红晕已经在闪）却仍然是米白色文字**，
  而口渴 5 变红。玩家看到红晕在跳、却找不到是哪个格子触发的。
- 低血渐晕（`vignetteParts`，8 条边缘带）生效了，红色确实在边缘脉动——
  这个是好的，保留。
- 但没有**图标**。四条属性靠「生命/饥饿/口渴/精力」四个词区分，
  危重时依然只能读字。

**根因**

- `GameScene.ts` `refreshStats()`（约 :2681）：`const urgent = mostUrgentStat(getGame().player)`，
  只有单个 `urgent` 参与变色（第 2684/2685 行 `setColor`）。
- `render/feedback.ts:104` `mostUrgentStat` 按归一化占比取**最低者**，
  四条都低于各自阈值时仍然只返回一个——这是「只许一条报警」的设计，
  不是 bug，但对「同时三条危急」的场景是错的产品决策。
- `STAT_BARS`（`GameScene.ts:196`）只有 `label` 字符串，没有 icon

**评委看到会怎么想**：红晕在闪、生命只剩 14，但 HUD 上那条仍然是米白色 ——
评委会先怀疑自己看错，然后怀疑这个 HUD 不传达信息。

**改法**

1. 分级变色：`< 25` 红、`25–50` 橙、`> 50` 正常。现在只有「最紧急的一条」变色，
   等于告诉玩家「另外三条不重要」，这是错的。
2. 每条属性加一个 12x12 图标（心/面包/水滴/闪电）。`STAT_BARS` 已经在一次
   遍历里画标签和数值，加 icon 只需多一个 `this.add.image`。

### M-7 数值增减没有方向色：涨跌同色，且根本没有「变化量」浮字 `[明显]`

**现象（实测代码 + 截图）**

- 全仓库**没有一处**「数值变化浮字」——喝一口水，头上不会飘 `+30`；
  玩家只能自己盯住 HUD 里那个两位数从 65 变成 95。`09b` 竖屏下这更要命，
  数值只有 14px。
- 唯一的增减表达是底部 `feedbackText` 一行字，而且**涨跌同一个颜色**：

  ```
  GameScene.ts:3201  `建造了 照明灯（-2 分钟）`     ← 损失时间
  GameScene.ts:4556  `使用 净水 · 水分 +30`          ← 获得水分
  两者都走 PALETTE.lightHigh #f4b66a（暖橙）
  ```

  也就是说「扣了 2 分钟」和「补了 30 点水分」在屏幕上长得一模一样。

**用户要求**（已写进 `VISUAL_SPEC.md` §2.5，硬约束）：
中国习惯是**涨红跌绿**，不是欧美的涨绿跌红。

**根因**

- `GameScene.ts` `flash()`（约 :2876）只有一个 `msg: string` 参数，
  没有 `tone` 参数，所以调用点无法表达方向。
- `feedbackText` 的颜色在 `buildHud()` 里一次性定死（`PALETTE.lightHigh`），
  之后再没改过。

**改法（低成本）**

1. `flash(msg: string, tone: 'gain' | 'loss' | 'neutral' = 'neutral')`，
   按 tone 分发到 `#e8907c`（涨）/ `#77c6a4`（跌）/ `#f4b66a`（中性）。
   改动约 10 行，调用点改上面列的 8 处（其中 4 处是纯涨/纯跌，直接给 tone 即可）。
   4921 / 4943 这种一句话两件事的，建议拆成两条 flash，或保留中性色只报净变化。
2. 浮动数值（`+30` 从角色头上淡出上飘）是**下一阶段**的事，约 40 行，
   需要一个新的 `Phaser.GameObjects.Text` 池。它的颜色也必须按 §2.5 走。

**评委看到会怎么想**：「我喝了水，屏幕没有给我任何即时反馈」——
这是生存游戏最基础的一条手感，缺失会被读成「战斗/数值还没做完」。

**优先改哪一条**：第 1 条（`tone` 参数）。它只碰 `flash()` 和两个调用点，
不新增任何对象，10 分钟能落。

## 6. 与《The Last Night》《This War of Mine》《Eastward》《Katana ZERO》的氛围差距

用户接受的参考方向：**冷青环境 + 局部暖光源 + 废弃建筑层次 + 减少装饰噪声突出物资**。

### 已经对上的部分

- **冷青 + 局部暖光**：对上了。`palette.ts` 的 16 色里只有 LIGHT 一族是暖色，
  这个约束执行得很彻底，第 1 层的蜡烛/第 5 层的火盆确实是画面上唯一的暖点。
- **废弃建筑层次**：对上了。「天花阴影 + 踢脚线 + 中层管道 + 地面杂物」四层结构
  在 `corridors.ts` 里是分层的，`04` 图里能看出前景/中景/背景。
- **减少装饰噪声**：部分对上。墙体细节（通风口、管夹、标识牌）密度是合适的，
  但**标签文字**本身成了新的噪声源（M-4：一屏 7 个标注）。

### 三个差距

1. **没有「离屏的第二层空间」**。《This War of Mine》的走廊两侧有门/窗/暗处，
   让画面有「更多空间在画面之外」的感觉。当前每一层是一个 1280x200 的横切面，
   左右两端直接被楼梯封死，视觉上像一条**被截断的走廊**而不是一栋楼的一层。
2. **光没有方向**。参考作品里暖光总是有明确方向（从门缝、从窗口、从台灯罩里侧漏），
   所以能读出「光源在哪」。当前 `lighting.ts` 的光是径向均匀衰减的圆形
   （`addGlow`），没有遮挡、没有投射，所以光斑看起来像贴上去的贴纸。
3. **人物与背景的明度差不够**。`11` 图里玩家角色与墙面的对比度偏低
   （`GameScene.ts` 夜幕遮罩的注释里自己也记录了 24.7 → 9.8 的实测），参考作品里人物通常
   是画面里**最亮或最暗的那一撮**，靠轮廓读人。

### 3 个最划算的改动（按性价比排序）

| 排序 | 改动 | 成本 | 收益 | 落点 |
|---|---|---|---|---|
| **1** | 夜幕加冷蓝色温 + 黄昏/黎明线性过渡 | ~20 行，纯函数 | 昼夜立刻可感；夜晚画面从「变暗」变成「变蓝」，氛围直接对齐参考方向 | `CraftingSystem.ts:97` + 夜幕遮罩 fill + `nightOverlayAlpha` |
| **2** | 光源加「锥形遮罩」——把圆形 glow 裁成一个从灯罩向下的半锥 | ~40 行 Graphics | 光有了方向，画面立刻从「贴纸」变成「有空间的房间」 | `lighting.ts` 的 `addGlow` 调用点，或新增 `addCone` |
| **3** | 人物加 1px 暖色轮廓光（rim light），只在有人工光源的一侧 | ~15 行 | 人物从背景里跳出来，解决「看不清人在哪」 | `walkcycle.ts` 的绘制流程末尾（**注意：该文件归 A2，我只提方案**） |

### 9.1 塔楼总览：本轮补审了（结果不好）

上一轮把 `TowerOverviewScene` 列在「未覆盖」里，本轮为了核对分辨率改动的
派生影响去看了一眼，发现它正是 640×360 的受害者：

`src/systems/TowerNav.ts:30` 的 `VIEW_H = 360` 是旧画布高度，而相机实际高 720。
后果不是「有点偏」，是**一个屏只用了上半部**：

```
e2e/screenshots/20-tower-overview.png（1280×800 视口，画布 1280×720 居中）
100 条楼层面板   y 36 .. 336         ← 300px（画布坐标）
视口坐标         y 76 .. 375         ← 逐像素扫出来的，比画布多 40px 上边距
画布可用高度      720
空白              y 336 .. 720       ← 384px，占了 53%
```

> **两个坐标口径别混用**：这份文档其他地方都用画布坐标，但截图文件是
> 1280×800 视口拍的，720 高的画布垂直居中，所以**视口 y = 画布 y + 40**。
> 上面两行是同一块区域。逐像素扫法（`node` 读 PNG 头 + `ffmpeg` 转 raw RGB，
> 按行统计饱和度 `max-min > 40 && max > 90` 的像素数，取 `>= 100` 的连续段）
> 得到 97 个密集段 + 300px 总跨度，300/100 = 3px 一条，与色带实际间距一致，
> 所以「100 条」这个数是对的，97 是抗锯齿边被阈值吃掉的结果。

截图里能直接看到：上半部是 100 条色带，下半部整片空背景。而这是
「100000 层」这个核心概念**唯一的产品呈现**——评委想看「这游戏多高」时，
看到的是半屏空。登记为 D-10，`[阻断]` 级，但**不在本文档的修复范围内**（要改
`src/systems/TowerNav.ts` 与 `src/tests/towerNav.test.ts`，且 `e2e/tower.spec.ts`
里 `expect(view.content).toBeLessThanOrEqual(360)` 这条断言建立在错误前提上，
必须一起改，否则改完必红）。

**这不是排版问题，是三处文档/常量没跟着画布翻倍**。D-1/D-2 是文档，D-6 是
注释，D-10 是**跑起来的布局**。四者同源。
