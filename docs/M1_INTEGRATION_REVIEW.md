## 必须关闭的问题

### 1. 攀爬时角色会被相机裁切：三种子已复现

[纵向 bounds](https://github.com/Zhuyuyangyy/floor-100000/blob/ea8538f/src/scenes/GameScene.ts#L591-L600) 在首层上楼和第五层下楼时不能覆盖完整的角色路径。只读帧采样确认，第 1 层上楼期间角色上端超出视口，第 5 层下楼末段角色几乎完全出框，随后落地重绘才恢复。其他中间楼层未在这组往返中检测到同类越界。

这些纵向 bounds 来自既有代码；本次两个收尾提交没有把这项问题关闭，不能简单归因为新增缺陷。最小修复方向是只在攀爬期间扩展纵向边界，覆盖目标落点及完整角色高度，落地后恢复常规 bounds；不需要重构 GameScene。

### 2. F 与旧攀爬可能叠加提交：代码路径确认，资金充足实测尚缺

[F 的绑定与 guard](https://github.com/Zhuyuyangyy/floor-100000/blob/ea8538f/src/scenes/GameScene.ts#L2667-L2710) 只做同帧去重，[近路入口](https://github.com/Zhuyuyangyy/floor-100000/blob/ea8538f/src/scenes/GameScene.ts#L2963-L2995) 没有 `stairClimb` 互斥。`clearFloor` 不清掉旧攀爬，而 [落地提交](https://github.com/Zhuyuyangyy/floor-100000/blob/ea8538f/src/systems/FloorSystem.ts#L105-L124) 不核验 `traversal.from`。

因此按代码，在 Seed 42、D1、第 2 层且至少有 114 金时，E 开始上楼后立刻按 F，可先付费到 4 层，再由旧攀爬多提交到 5 层。这是基线已存在的状态竞态，并非本轮两个提交新引入；本轮没有通过注入金币去冒充真实复现。应先阻止攀爬中的 F，再为陈旧 traversal 增加状态校验及回归测试，不改变定价公式。

### 3. F 显示价格与实际需求不一致：真实输入已复现

[提示](https://github.com/Zhuyuyangyy/floor-100000/blob/ea8538f/src/scenes/GameScene.ts#L3540-L3543) 用原始 skip 报价，[执行](https://github.com/Zhuyuyangyy/floor-100000/blob/ea8538f/src/scenes/GameScene.ts#L2976-L2980) 则先按剩余楼层截断。Seed 42、D1、第 4 层，井口显示 **128 金**，按 F 后却提示实际需要 **108 金**。Seed 1、2026 同层分别显示 138 / 118 金，实际都需要 108 金；Seed 2026 第 2 层也显示 134、实际需要 124。

资金不足时，本轮均验证金币、楼层和近路次数不变。成功付费、落点与攀爬中 F 的资金充足真实流程仍未验证，不能据此标记全部 F 验收通过。这项报价问题同样是基线已有；提示与执行应共用截断后的 skip，不重做经济系统。

### 4. E2E 与 CI 仍是红灯

修复输入准备、交互等待及楼梯落地等待的脆弱 helper，并在修复后重跑完整本地 E2E 和 GitHub Actions。不能删掉失败项、只跑通过子集、增加状态注入，或仅更新文档数字就放行。
