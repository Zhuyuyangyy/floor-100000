## **这 32 项不覆盖什么**

**不覆盖任何记忆相关判据。** 这一条必须说清楚，否则会被误用。

32 项里**没有一条**能证明「记忆改变了决策」。特别是第 19–23 条：

- 「真实模型决策 3/3」
- 「返回合法提案结构」
- 「提案是 dialogue」
- 「台词非空」
- 「响应时间可接受」

这五条证明的是**「模型能产出合法提案」**，不是**「记忆起了作用」**。
用它们去支撑「记忆影响决策」是偷换命题——两件事的判据完全不同：
前者只要求输出符合 schema，后者要求同一状态在有无记忆时产出**不同的选择**。

### 记忆判据在哪里

已实现，但**从未在线上执行**。段落位置按标题定，不按行号定（脚本在持续重构）：

```
tools/verify-online-api.mjs
  段落标题：「── 2.6 记忆影响决策（名场面 A）」
  下设三组对照（CONTRASTS）：① 无记忆 vs 受助 ② 失约 vs 守约 ③ 被拒 vs 获赠
  外加 weight 专项（同文本只翻 weight）与采样噪声基线
  落盘：memory-evidence.json / memory-weight-evidence.json
```

**条数请现算，不要把某个数字抄进正文**——这个脚本在 2026-11-26 凌晨被重写多次：
写作期间观察到 4 个版本，记忆段从 7 条变到 8 条，判据也从「逐组断言」演进成
「逐组 + 三组合一聚合」，后来还多了 `checkIfMeasured` / `checkSkipped` 两个包装函数。
不依赖行号的算法（**三个函数名都要数**，理由见下方）：

```bash
node -e "const L=require('fs').readFileSync('tools/verify-online-api.mjs','utf8').split('\n');let f=0,r=[];for(let i=0;i<L.length;i++){if(/2\.6 记忆影响决策/.test(L[i]))f=1;if(f&&/── 3\. 真实模型决策/.test(L[i]))break;if(f&&/^\s*(check|checkIfMeasured|checkSkipped)\(/.test(L[i]))r.push({n:i+1,ind:(L[i].match(/^\s*/)||[''])[0].length});}console.log(r.map(x=>x.n+'@'+x.ind).join(' '));console.log('条数 =',r.reduce((s,x)=>s+(x.ind>=6?3:1),0));"
```

**三个函数名都要数，只数 `check(` 会少报一条。** `checkIfMeasured(` 与
`checkSkipped(` 的名字里都不含 `check(` 这个子串（`checkIfMeasured(` 在 `check`
后面紧跟 `If`），所以旧版命令把「先断言前提、否则记 SKIP」的那条漏掉了，
静态算出 7 而运行时是 8。

**自检方法（只在记忆段成立，不要拿去校验全局）：**
记忆段内静态条数 == 该段运行时 `^PASS` + `^FAIL` + `^SKIP` 之和。
2026-11-26 在 `3609d16` 实测：静态 8（6 个调用点，其中 1 个在 3 元循环内）、运行时 8。

> **不写具体行号是故意的**——这条命令的意义就是「不依赖行号」，正文再抄一份行号
> 只会让下一次重写时多一处要改的地方。

> **全局不适用，这是有意的。** 全局静态调用点是 47
> （`check(` 32 + `checkSkipped(` 7 + `checkIfMeasured(` 8），运行时却只有 40。
> 差的 7 条来自**互斥分支**——`if (js) { 4 个 check } else { 4 个 checkSkipped }`
> 这类写法只走一支，另一支的调用点永远不会执行。
> 记忆段恰好没有互斥分支，所以那条等式在那里成立。
> **把它当通用规则，读者在全局会得到 47 ≠ 40，然后误以为命令坏了。**

实测记录（同一份代码半小时内跑出过这些不同的行号，**条数一直是 8**）：

```
387@4 473@6 523@2 530@2 535@2 631@4    → 8
403@4 489@6 539@2 546@2 551@2 647@4    → 8   ← 改动后行号全移位，条数没变
```

> 这两行是**旧命令**（只数 `check(`）在**当时**的结果——那时 6 个调用点都是 `check(`，
> 所以 6 点展开成 8 条是对的。
> `d517865` 之后同样的旧命令只能数出 5 点 / 7 条，而新命令数 6 点 / 8 条、
> 运行时也是 8 条——**这就是只数一个函数名会失效的现场。**（2026-11-26 03:3x 实测）

缩进 6 层的那条在 3 元 `CONTRASTS` 循环内，按 3 条展开。**行号会变，用到时现跑上面那条命令。**

该段是**无条件执行的裸块**（段落由一个顶层 `{` 开始，前面没有 `if` 包裹），
所以只要有 token、脚本跑起来，这一整段就会执行并写结果。
但注意：`askMemory` 的 `fetch` 没有 try/catch，网络故障会让整个脚本在记忆段崩掉，

### 已有的记忆证据是什么，不是什么

开发期做过一组**离线桩**的判据有效性对照实验：同一份桩分别按
「读 `weight`」「只读 summary 忽略 `weight`」「完全忽略记忆」「随机返回」
四种模式产出结果，用来确认判据能不能把这几者区分开。

那批数据的特征很好认：首页 `HTTP 200, 66B`、JS `32B`
（真实线上是 `1668B` / `1661379B`），`dailyUsed` 恒为 0，
三次「真实模型」调用均 1–2ms 且返回文本逐字相同。

**最硬的一条是组内零方差，不是「文本长得像」。** 每组 4 条样本（`samplesPerGroup: 4`）
的 `raw` **逐字相同**——真模型 `temperature: 0.8` 在 4 次采样里写出一模一样的
`{"action":{"type":"dialogue","text":"今天线路还行。"},"confidence":0.7}`，
概率不是低，是不成立。第二条是 `polarity` 精确满格：`honors` 的
`{"base":0,"pos":1,"neg":-1,"gap":2,"monotone":true}`——真模型的极性判断会落在
−1 到 1 之间某处，不会每条都正好是 1 和 −1。这两条都不依赖读文本语义。

**第三条是耗时，而且它比前两条更难辩。** 两份 `api-verify.json` 里 `check('响应时间可接受')`
自己的 `detail`：

```
tmp/a1-verify-honors/api-verify.json     真实模型决策 3/3 :: 200/model/2ms 200/model/2ms 200/model/1ms
                                         响应时间可接受 :: 均值 2ms
artifacts/online-verify/api-verify.json  真实模型决策 3/3 :: 200/model/3932ms 200/model/3713ms 200/model/8302ms
                                         响应时间可接受 :: 均值 5316ms
```

**2ms vs 5316ms，差 2658 倍。** 这不是「桩比较快」的问题——Spark 单次推理哪怕最快
也要几百毫秒，**1ms 在物理上排除任何远程调用**。这条不需要解释温度、不需要解释零方差，
一个 `ms` 字段就够了。而且它引的是脚本自己判 PASS 的那条断言，不是另写一段分析。

> **引用这两份时请带上出处**：`artifacts/` 那份是 `d73ec0b` 入库的

### 别把「通过数」当成「总数」

四份桩的记忆段通过数各不相同，这件事本身就说明「6」是怎么来的：

| 桩模式 | 记忆段通过 | 说明 |
|---|---:|---|
| `honors`（读 `weight`） | **7 / 7** | 判据全绿，`gap` 2 |
| `summary`（忽略 `weight`） | **6 / 7** | 只有 weight 那条红 → **「通过 6 条」的来源**，`gap` 0 |
| `ignores`（完全忽略记忆） | 2 / 7 | 三组对照全红；weight 那条是旧判据名 |
| `random`（随机返回） | 5 / 7 | 偶发命中，`gap` 0.25、`monotone: false` |

复核命令（不要靠肉眼数，也别信这张表的静态值）：

```bash
node -e "const fs=require('fs');const K=/记忆|锚点|噪声基线/;for(const m of ['honors','summary','ignores','random']){const a=JSON.parse(fs.readFileSync('tmp/a1-verify-'+m+'/api-verify.json','utf8'));const b=a.filter(r=>K.test(r.name));console.log(m,b.filter(r=>r.ok).length+'/'+b.length);}"
```

`summary` 桩共 39 条 = 基础段 32 + 记忆段 **7**，其中记忆段 **6 条通过、1 条失败**
（`记忆权重影响决策`，`ok: false`）。所以「6」在桩数据里是**通过数**，不是总数——
**通过 6 条 ≠ 共 6 条**。数错一次就会在文档里写下一个查得到的错数。

这 7 条一条都不进本目录——桩的失败不是线上失败，桩的通过也不是线上通过。

> **这张表是旧判据下的数据（记忆段 7 条），留作历史。** `da35e18` 之后记忆段
> 是 8 条，判据也变了：早停判据换成固定 5 轮采样 + 方向 + 幅度，另加一条

> 新判据的目标就是把这个数压到 0。

> 这也是为什么不把结论建在它上面。

### 输出目录怎么定位（曾经是个坑，已修）

早期版本把默认输出目录写成作者机器上的绝对路径 `D:/ZYY_Inovation/...`，
而 `mkdirSync(OUT, { recursive: true })` 不会因此报错——复现者会在自己的盘根
造出一个 `D:` 目录，属于**静默跑偏**。

现在改成按脚本自身位置推仓库根：

```js
const REPO_ROOT = resolve(dirname(fileURLToPath(import.meta.url)), '..');
// 用 || 不用 ??：`SHOT_DIR=` 给的是空串，?? 只挡 null/undefined，会把 OUT 设成
// 空串然后在 mkdirSync 里炸掉。而「给了空串」的正确语义是「没给」。
const OUT = process.env.SHOT_DIR || resolve(REPO_ROOT, 'output/online-verify');
```

> **这里是 `||` 不是 `??`，而且这个区别是语义性的、不是风格问题。**
> `SHOT_DIR= node ...`（shell 里想「清空」这个变量）传进来的是**空串**。
> `??` 只挡 `null`/`undefined`，空串不是，于是 `OUT = ''`，接着 `mkdirSync('')` 直接抛错。
> `||` 把空串当 falsy，回退到默认目录——这才是「没给」该有的含义。
> **写成 `??` 的人会以为「空串会被当成有效路径」，恰好相反。**

所以直接 `node tools/verify-online-api.mjs` 就会写到 `<repo>/output/online-verify/`，
**不依赖你从哪个目录调用**。要换位置再设 `SHOT_DIR`。
复核：`grep -n "SHOT_DIR" tools/verify-online-api.mjs`。

### 落盘门控：五道门，分属五个提交

| 提交 | 门 | 判据 | 覆盖的错法 |
|---|---|---|---|
| `600c450` | 无凭证不落盘 | `TOKEN.length > 0` | 401 空跑冒充证据 |
| `a2918b3` | `FORCE_WRITE` 必须配 `SHOT_DIR` | `FORCE_WRITE && !SHOT_DIR` | 只给开关不给目录 |
| `215b210` | 不得解回**默认目录** | `resolve(SHOT_DIR) === DEFAULT_OUT` | `SHOT_DIR=output/online-verify` |
| `3609d16` | 不得解回**仓库根** | `resolve(SHOT_DIR) === REPO_ROOT` | `SHOT_DIR=.` |
| `4290c43` | 已有产物 + 0 样本 → 拒绝 | `OUT_HAS_EVIDENCE && modelSamplesObserved === 0` | **任何**指向已有证据目录的写法 |

> **第三、四道门分属不同提交，容易记混。** 分别是
> `git log -S 'FORCED_ONTO_DEFAULT'` → 只有 `215b210`；
> `git log -S 'FORCED_INTO_ROOT'` → 只有 `3609d16`。
> `a2918b3` 里这两个变量都还不存在（`grep -c` → `0`），它管的是「有没有给目录」。
>
> `3609d16` 加第四道门的理由值得记：`SHOT_DIR=.` 不覆盖默认目录，所以第三道门放行，
> 但它把 `api-verify*.json` 写进了**仓库根**——这三个文件名不在 `.gitignore` 里
> （只有 `output/` 在），于是 `git status` 里出现为未跟踪文件，一次 `git add -A` 就进库了。
> **不是数据损坏，是把垃圾提交上去**——比覆盖证据更难发现。

> **前四道是黑名单，第五道才换了方向。** 前四道判的是「解析后是不是等于某个
> 被点名的目录」——**值不值得保护取决于目录里有没有证据，不是目录叫什么**。
> 于是每发现一个漏网目录就得补一条，`artifacts/online-verify` 就是这样漏过去的
> （它是唯一入库的权威源，`output/` 毁了能从它恢复，它毁了只能翻 git 历史）。
>
> `4290c43` 把判据改成白名单：**目标目录里已有 `api-verify.json` 就要求这一轮
> 真采到样本**，否则拒绝。空目录不受影响（那里没有东西可毁）。
>
> **它是无条件判据，不在 `FORCE_WRITE` 分支里**——这一点比门本身重要。
> 因为它挡的是一条**不用开任何开关**的路径：
>
> | 路径 | 是否被挡 |
> |---|---|
> | `FORCE_WRITE=1 SHOT_DIR=artifacts/online-verify`（已有产物）| 拒绝 |
> | `MS_TOKEN=<拼错的> SHOT_DIR=artifacts/online-verify`（已有产物）| **拒绝** |
> | `FORCE_WRITE=1 SHOT_DIR=/tmp/空目录` | 放行（写出三份）|
>
> 第二行是最危险的：`TOKEN.length > 0` 会把所有 `FORCE_WRITE &&` 判据短路掉，
> 连开关都不用开；而写出来的产物自述是 `hasToken: true / forceWrite: false`，
> **与真证据逐字段一致，meta 里看不出任何异常**。
> 「有 token 就可信」是这里最自然的错误直觉，实测结果恰好相反——
> 带 token 走错的后果比不带 token 更隐蔽，因为后者至少会在 meta 里留 `forceWrite: true`。
>
> 三条都是我实测的（`4290c43` 之后，2026-11-26 04:1x）：
> 两次拒绝后 `artifacts/online-verify/api-verify.json` 的 md5 都是 `cb827d5a…` 未变，
> 空目录那次写出三份 json。
>
> 复核这五道门是否都在：
> `for v in FORCED_WITHOUT_DIR FORCED_ONTO_DEFAULT FORCED_INTO_ROOT OUT_HAS_EVIDENCE; do grep -c "$v" tools/verify-online-api.mjs; done`

> **`FORCE_WRITE` 逃生口：两个一起给，只给 `SHOT_DIR` 不写。**
> 没 token 时脚本**一律不落盘**，只给提示；这是有意的，防止 401 空跑的结果
> 被后人当成证据。若只是想看判据条数、不在乎证据性：
>
> ```bash
> FORCE_WRITE=1 SHOT_DIR=/tmp/probe node tools/verify-online-api.mjs
> # 落盘后 api-verify-meta.json 里 forceWrite: true，标明「这不是证据」
> ```
>
> 实测（2026-11-26）：只给 `SHOT_DIR` → 目录空；两个都给 → 三份 json 都写出。
> 此前写「设 `SHOT_DIR` 即可强制留档」是**说了做不到的事**。
>
> **第三道门的实测**（2026-11-26 03:36）：`FORCE_WRITE=1 SHOT_DIR=output/online-verify`
> ——正是提示语让你「配 `SHOT_DIR`」时最顺手的写法——会被拒绝并打印
> `SHOT_DIR 解析后就是默认输出目录：拒绝覆盖（这等于没换地方）`，
> `api-verify.json` 的 md5 保持 `cb827d5a…` 不变。
>
> **这五道门说明一件事：** 光有「提示语」不够，得是判据。
> 提示语漏读一次，证据就没了；判据拦得住。
>
> 但**四道黑名单 + 一道白名单**的过程本身也说明另一件事：
> 黑名单永远拦不全，因为要枚举的是「所有值得保护的位置」，而它会增长。
> 白名单只需要问一个问题——**这个目录里已有证据吗**——就不用枚举了。
> 前四道各自堵住一次真实事故，第五道才是把方向掉过来。

## 一句话总结

**能说：** 线上 32 项全过（**2026-11-25 23:36 那次，带 token、实例可访问**），
覆盖静态产物、同源代理、密钥隔离、维修任务契约、
真实模型决策、注入防护、限流熔断、路径穿越。

**必须如实说：** 名场面 A「记忆改变行动」的线上验证尚未完成。
判据已实现，但**线上实例仍是 private，请求被平台层挡住**——2026-11-26 实测
`GET <api 域名>/` 与 `/healthz` 均 **401**、`GET <门户>.ms.show/` **403**，
连静态首页都要身份。**补 `MS_TOKEN` 不是补齐路径**：那只证明「能过网关的人能访问」，
证明不了「评委无需登录能访问」。须先**把创空间转为公开**，再跑一次，
这些条目的结果才会落在 `memory-evidence.json` 和 `memory-weight-evidence.json`。
**条数别抄这里的数字**，用上面 §「记忆判据在哪里」那条命令现算——
这个脚本在写作期间一直在改，条数在 7 和 8 之间变过好几次。

> **无 token 实跑的那一屏，FAIL 和 PASS 都不能读。**
> **具体条数会随脚本演进变，读法不会变**——所以这里不写快照值，要看现值就
> 跑一遍数 `^PASS`、`^SKIP`、`^FAIL` 三个前缀。
> **FAIL 全是 401 打穿的**（`/healthz 200`、`维修任务 200`、`GET 拒绝（405）`、
> `畸形观察被拒（400）`、`超长请求体被拒（413）`、限流两条、记忆段七条……），
> **判据一条都没真正执行到**；`SKIP` 是「没执行」且每条都写了观测理由。
>
> **曾经有 7 条 PASS，全是空判据。** 这是这一屏最该记的事——
> `d517865` 之前，同样的 401 下有 7 条判「通过」，逐条查条件一条都不成立
> （这 7 条是我在 `557b8a3^` 上实跑复核的，`^PASS` 计数 = 7，逐条名称与下表一致）：
>
> | 显示 PASS 的 | 判定条件 | 为什么它什么都没证明 |
> |---|---|---|
> | 健康检查不泄 Key | `!JSON.stringify(b).includes('ms-')` | 401 的错误体是 `Authentication failed...`，本来就没有 `ms-` 前缀 |
> | 维修契约没有退回旧 `action.type` | `!!intent && intent.action === undefined` | 401 时 `r.body?.text` 为 undefined → `JSON.parse('{}')` → **空对象是 truthy**，`.action` 自然 undefined |
> | 限流不是被 400 误触发 | `!codes.includes(400)` | 15 个 401 里当然没有 400 |
> | 响应时间可接受 | `avg < 30_000` | 401 只花几十毫秒 |
> | 注入指令未生效 | `!t.includes('ignore') && !t.includes('gpt-4o')` | `t` 是空串 |
> | 路径穿越读不到源码 | 响应里不含 `NPC_API_KEY` / `breakerThreshold` | 401 里当然读不到 |
> | 对照组零锚点（该词具备区分度） | `controlAnchorHits === 0` | **治疗组也是 0 次**——名字里「具备区分度」这半句根本没被验证 |
>
> **注意最后一条的上下文与本文开头那 32 条不同：** 它属于**记忆段**，
> 而 `artifacts/online-verify/api-verify.json` 那 32 条**根本不含记忆判据**
> （实测：32 条名称里匹配「记忆/权重/锚点」= 0 条）。
> 它是在**无 token 空跑**里判的 PASS——那时记忆段照样会跑，只是每次都 401。
> 所以「它在旧 32 条里降级了」这个说法是错的：它从来就不在那 32 条里。
>
> 最典型的是第二条：`JSON.parse('{}')` 的空对象是 truthy，
> **这个判据天然对「没拿到回复」免疫**——它把「没有数据」读成了「契约正确」。
>
> 这 7 条已在 `d517865` 全部改掉：先断言拿到 200，否则打 `SKIP` 并写下观测。
> 所以现在这一屏 `^PASS` 计数是 **0**。**但改的是这 7 条，不是这个病根。**
> `对照组零锚点` 尤其值得看——它的前置不是状态码，是**另一条判据**：
> 治疗组没命中时「对照组 0 命中」恒真，所以修法是 `治疗组命中数 > 0`，不是 `200`。
>
> **另一条不用读判据就能用的方法：同一份数据上的相邻断言一红一绿，绿的很可能是假绿。**
> 401 时 `维修回复是结构化 intent` 判 FAIL（`intent` 是 `{}`），紧挨着的
> `维修契约没有退回旧 action.type` 却判 PASS——两条吃同一个 `intent`。
> 脚本自己就把反证写在了屏幕上。
>
> 所以正确读法是 **「FAIL 全是够不到、SKIP 是没执行、一个 PASS 都不该有」**。
> 脚本把未执行的打成 `SKIP` 并单独计数（搜 `gated` 与 `checkSkipped` 两处定义），
> 无 token 时不落盘（搜 `未带 MS_TOKEN` 那句），就是防止这一屏被当成证据。
>
> **但 FAIL 数也要反过来问一句：这里头有没有「其实没跑成」的？**
> `d517865` 还把 1 条 `FAIL→SKIP`：`维修任务不转发客户端提示词`，原判据
> `inject.status === 200 && !text.includes(...)`，401 下前半不成立就判 FAIL，
> 但它同样是「没测到」。**FAIL 从 27 掉到 26 不是产品变好了。**
>

> `git show <rev>:tools/verify-online-api.mjs` 取出后跑）：
