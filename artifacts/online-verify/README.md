> **「路径穿越」那一条要单独说，它是这 32 条里唯一一条我看着它 PASS 却撤掉结论的。**
>
> 它当时记录的是 `ok: true, detail: "HTTP 200"`。但 `HTTP 200` 恰恰不是「穿越被挡住」的
> 证据——`serveStatic` 对任何不存在的路径都回退 `index.html`，那是 SPA 的常规行为。
> 更关键的是**载荷根本没发出去**：脚本用的是 `get('/../server/npc-proxy.mjs')`，
> 内部 `fetch(\`${BASE}${path}\`)`，而 WHATWG URL 在**客户端**就把 `/../` 规范化掉了。
>
> 我用一个只记录 `req.url` 的桩取证（`node .vchk/probe.mjs` 那类写法）：
>
> | 客户端 | 服务端实际收到 |
> |---|---|
> | `fetch(BASE + '/../server/npc-proxy.mjs')` | `/server/npc-proxy.mjs` ← **折叠了** |
> | `http.request({ path: '/../server/npc-proxy.mjs' })` | `/../server/npc-proxy.mjs` ← 原样 |
>
> 所以这条判据实际问的是「`/server/npc-proxy.mjs` 取不到源码」，
> 而它想要问的是「**穿越**取不到源码」。两句话不是一个意思。
>
> 我做了对照实验来确认它没有区分力。**这里我第一版写错了，先说清楚错在哪：**
> 我原来只用了**一种** naive 服务端（不解码，直接 `join(ROOT, url)`），却把结论
> 写成了「`/%2e%2e%2f` + `fetch` 也不泄漏」。a5 和 a1 各自用**先解码**的 naive
> 服务端复现，得到相反结果。**差异在装置，不在结论**——naive 有两种，都叫 naive：
>
> - **N1 不解码**：`join(DIST, url)` —— `%2e` 不是 `.`，`join` 看不懂，落兜底页
> - **N2 先解码**：`join(DIST, decodeURIComponent(url))` —— `%2e%2e` 被解回 `..`，越界
>
> 线上 `server/npc-proxy.mjs:510` 第一件事就是 `decodeURIComponent`，所以**真实服务端
> 属于 N2 那一类**。我那张表若只标「naive」，下一个换装置复现就会得到相反结果。
>
> 重测（2026-11-26，真实仓库布局 `dist/` + `server/`，`fetch` 与 `http.request` 各一发）：

| 装置 | 载荷 | `fetch` | `http.request` |
|---|---|---|---|
| **N1 不解码** | `/../server/npc-proxy.mjs` | 200 / 1716B / 无符号 | 200 / 28513B / **有符号** |
| N1 | `/..%2fserver/npc-proxy.mjs` | 200 / 1716B / 无符号 | 200 / 1716B / 无符号 |
| N1 | `/%2e%2e%2fserver/npc-proxy.mjs` | 200 / 1716B / 无符号 | 200 / 1716B / 无符号 |
| **N2 先解码** | `/../server/npc-proxy.mjs` | 200 / 1716B / 无符号 | 200 / 28513B / **有符号** |
| N2 | `/..%2fserver/npc-proxy.mjs` | 200 / 28513B / **有符号** | 200 / 28513B / **有符号** |
| N2 | `/%2e%2e%2fserver/npc-proxy.mjs` | 200 / 28513B / **有符号** | 200 / 28513B / **有符号** |

> **两个必须一起读的结论：**
>
> 1. **第一行（`/../` + `fetch`）在两种装置里都是「无符号」**——所以
>    「脚本那条判据从来没测到穿越」这个结论**与装置无关**，成立。
>    这就是它可以作废的依据，它不依赖我选哪种 naive。
> 2. **`/..%2f` 和 `/%2e%2e%2f` 的结果依赖装置**：N1 下 `fetch` 送不到，N2 下送得到。
>    我原表把 N2 的结果写在了「naive」名下，**等于混用了两种装置**，这是我的错。
>
> **单位也要说清**：表中 `1716B` / `28513B` 是**响应体字节数**（`Buffer.length`，
> `wc -c` 量到的）。脚本 `detail` 里打印的 `${txt.length}` 是 **JS 字符串长度**
> （UTF-16 码元），同一份文件是 **1702 / 23232**。两者差 1.01 倍 / 1.23 倍，
> 因为文件里有中文。**别把 `28513` 和 `23232` 当成两个不同的文件**——
> 它们是同一个 `server/npc-proxy.mjs` 的字节数与字符数。
>
> 所以这条**不能作为安全边界证据**。它从 `492eab0` 起就在，不是这轮引入的。
> **正确的说法是：这条判据已作废，不再进入计数。**
> 不留「等补旁证再复活」这个活口——原因见下两节：它的证伪范围太窄，
> 而且**它连 dist 外的其它文件都漏判**。
>
> 这不影响其余 31 条——它们是各自独立的判据，与这一条无关。但它确实意味着
> 「32 项全过」那句里，**有一条的通过理由不成立**。
>
> 另外：`对照组零锚点（该词具备区分度）` **根本不在 32 条里**——它是记忆段的判据，
> 这份快照没跑记忆段。所以它既不会「降级」，也从来不是这 32 条的一部分。

**逐行说明为什么这样判（这一节比结论重要）：**

- **第 ② 行是这一节的要害。** `safePath` 有两道独立防线：

  ```js
  const decoded = decodeURIComponent(...);
  const candidate = resolve(join(DIST_ROOT, normalize(decoded)));   // 第一道：normalize 吃掉前导 ..
  if (candidate !== DIST_ROOT && !candidate.startsWith(DIST_ROOT + sep)) return null;  // 第二道
  ```

  `normalize('/../x')` → `'\x'`，前导 `..` **在第一道就被吃掉了**。所以只删第二道不漏、
  判据也 FAIL 不了。**这条判据证伪的是「能被 `/../` 读出 dist 外的源码」，
  不是「越界比对那一行还在」。** 要证明第二道还在，只能读代码或改代码做对照。
  （我最早写「删越界比对 → 判据失效」是错的；a5 最早写「只删越界比对就漏」也是同一误判。
  两次独立踩进同一个坑，说明这个错读起来很像对的。）

- **第 ③ 行是旧判据的第二个 bug，`9db9ec8` 修的正是它。** 服务端**真的拒绝了**（403），
  旧判据却把它读成「鉴权层就挡住了，没测到路径解析」，记 SKIP。可这个服务端
  **根本没有鉴权层**——`401` 在 `server/npc-proxy.mjs` 里出现 **0 次**，
  403 只有一处来源（`safePath` 返回 `null` 的那个分支），静态资源不带 token 也是 200。
  **「防护生效」和「没测到」必须是两个不同的结论**，把前者读成后者等于白丢一条正面证据。
  （a1 先发现，我又在代码里核了一遍 `401` 计数。）

- **第 ⑥⑦ 行是新判据必须记 SKIP 的情形。** 基线自己都不可用（401/403/405/429 或 5xx），
  比对就没有意义。**这一格很容易写错**：如果只看「载荷和基线一样」就判 PASS，
  一个连静态资源都不服务、全 405 的服务端会被判成 PASS。a1 的写法是

## 复核这条时顺手抓到的第二件事：畸形 URL 能把服务打死

**这不是「判据假绿」，是服务端真的会挂。** 我本来只打算核穿越那一条，结果在测
「服务端收到了什么」的时候，一个畸形载荷把桩打退了，于是拿真服务端复了一遍。

### 症状

```bash
PORT=18260 HOST=127.0.0.1 NPC_API_KEY= node server/npc-proxy.mjs
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:18260/healthz   # 200
printf 'GET /%% HTTP/1.1\r\nHost: x\r\nConnection: close\r\n\r\n' | <raw socket>  # 连接被重置
curl -s -m 3 -o /dev/null -w "%{http_code}\n" http://127.0.0.1:18260/healthz   # 000，连不上
```

服务端日志：

```
server/npc-proxy.mjs:510
  const decoded = decodeURIComponent(urlPath.split('?')[0].split('#')[0]);
                  ^
URIError: URI malformed
    at safePath (server/npc-proxy.mjs:510:19)
    at serveStatic (server/npc-proxy.mjs:518:16)
    at Server.<anonymous> (server/npc-proxy.mjs:668:11)
Node.js v22.22.2
```

**进程退出，端口不再监听。** 一个请求，一次重启。

### 逐条实测（2026-11-26，工作区 `server/npc-proxy.mjs`，该文件自 `6cef682` 起未改动）

每条都是**新起一个进程**再发一个请求，然后用 `/healthz` 复查进程是否还活着：

| 方法 | 载荷 | 进程 | 响应首行 |
|---|---|---|---|
| GET | `/` | 活 | `HTTP/1.1 200 OK` |
| GET | `/healthz` | 活 | `HTTP/1.1 200 OK` |
| GET | `/%` | **❌ 死** | `ECONNRESET` |
| GET | `/%2` | **❌ 死** | `ECONNRESET` |
| GET | `/%zz` | **❌ 死** | `ECONNRESET` |
| GET | `/index.html%` | **❌ 死** | `ECONNRESET` |
| GET | `/%E0%A4%A` | **❌ 死** | `ECONNRESET` |
| HEAD | `/%` | **❌ 死** | `ECONNRESET` |
| GET | `/a?b=%` | 活 | `HTTP/1.1 200 OK` |
| GET | `/%25` | 活 | `HTTP/1.1 200 OK` |
| GET | `/api/npc/decide` | 活 | `HTTP/1.1 405` |
| GET | `/%00` | 活 | `HTTP/1.1 200 OK` |

12 条里 **6 条能打死进程**。三个细节值得记：

- **`/a?b=%` 活，`/%` 死。** 因为 `safePath` 先 `split('?')[0]` 再去 decode，
  查询串里的坏编码根本走不到 `decodeURIComponent`。所以**打点必须落在 path 上**。
- **`HEAD` 和 `GET` 一样死**——`serveStatic` 对两者走同一条路，不是只有 GET 有风险。
- **`/%00` 不死**：`%00` 是合法的百分号编码（decode 成 NUL 字符），
  它死在后面的文件系统调用上，不死在 decode。**「能打死」和「编码怪」不是一回事。**

### 原因，四层叠起来才致命

```js
const server = createServer(async (req, res) => {      // ① async 回调，没有 try
  ...
  if (req.method === 'GET' || req.method === 'HEAD') {
    await serveStatic(req, res);                        // ② 没有 try
```

```js
function safePath(urlPath) {
  const decoded = decodeURIComponent(...);              // ③ 这一行裸奔，可能抛 URIError
```

④ 全文件没有 `process.on('unhandledRejection')`。Node 15 起未处理的 rejection
**默认让进程退出**，不是警告。四层里任何一层补上都不会挂——但一层都没有。

### 它和线上验收证据是什么关系

**不影响那 32 条的数据**，因为从来没有任何一条判据发过畸形 URL：

```bash

```

（真跑过：`0`。脚本里既没有 `decodeURIComponent`，也没有任何一条断言期待 404。）

「畸形观察被拒（400）」测的是**请求体**字段畸形（`POST /api/npc/decide` 的 JSON），
和 URL 编码无关。所以这是个**覆盖缺口**，不是数据污染。

**但这个 bug 在产出证据的那一刻就已经存在了。** 溯源：


也就是说：**你手上这份「31/32 项通过」的证据，是在一个「一个请求就能打死」的服务上
跑出来的，而且它没测到这件事。** 这不是证据造假，是证据的范围没覆盖到。

**三个函数名都要数，只数 `check(` 会少报一条。** `checkIfMeasured(` 与
`checkSkipped(` 的名字里都不含 `check(` 这个子串（`checkIfMeasured(` 在 `check`
后面紧跟 `If`），所以旧版命令把「先断言前提、否则记 SKIP」的那条漏掉了，
静态算出 7 而运行时是 8。

**自检方法（只在记忆段成立，不要拿去校验全局）：**
记忆段内静态条数 == 该段运行时 `^PASS` + `^FAIL` + `^SKIP` 之和。
2026-11-26 在 `3609d16` 实测：静态 8（6 个调用点，其中 1 个在 3 元循环内）、运行时 8。

> **不写具体行号是故意的**——这条命令的意义就是「不依赖行号」，正文再抄一份行号
> 只会让下一次重写时多一处要改的地方。

> **全局不适用，这是有意的。** 全局静态调用点是 47
> （`check(` 32 + `checkSkipped(` 7 + `checkIfMeasured(` 8），运行时却只有 40。
>
> 这 7 条差额**不是「7 条互斥分支」**，是三种效应的净结果（2026-11-26 在 `d0304d3` 实测分解）：

> | 记忆段 `记忆改变决策：…` 在 3 元循环内，展开成 3 条 | +2 | 1 个调用点 → 3 条记录 |
>

> 所以那条等式在那里成立。**把它当通用规则，读者在全局会得到 47 ≠ 40，
> 然后误以为命令坏了。**

### 输出目录怎么定位（曾经是个坑，已修）

早期版本把默认输出目录写成作者机器上的绝对路径 `D:/ZYY_Inovation/...`，
而 `mkdirSync(OUT, { recursive: true })` 不会因此报错——复现者会在自己的盘根
造出一个 `D:` 目录，属于**静默跑偏**。

现在改成按脚本自身位置推仓库根：

```js
const REPO_ROOT = resolve(dirname(fileURLToPath(import.meta.url)), '..');
// 用 || 不用 ??：`SHOT_DIR=` 给的是空串，?? 只挡 null/undefined，会把 OUT 设成
// 空串然后在 mkdirSync 里炸掉。而「给了空串」的正确语义是「没给」。
const OUT = process.env.SHOT_DIR || resolve(REPO_ROOT, 'output/online-verify');
```

> **这里是 `||` 不是 `??`，而且这个区别是语义性的、不是风格问题。**
> `SHOT_DIR= node ...`（shell 里想「清空」这个变量）传进来的是**空串**。
> `??` 只挡 `null`/`undefined`，空串不是，于是 `OUT = ''`，接着 `mkdirSync('')` 直接抛错。
> `||` 把空串当 falsy，回退到默认目录——这才是「没给」该有的含义。
> **写成 `??` 的人会以为「空串会被当成有效路径」，恰好相反。**

所以直接 `node tools/verify-online-api.mjs` 就会写到 `<repo>/output/online-verify/`，
**不依赖你从哪个目录调用**。要换位置再设 `SHOT_DIR`。
复核：`grep -n "SHOT_DIR" tools/verify-online-api.mjs`。

> ```
>
> 预期：`EXIT=1`、打印「拒绝覆盖：… 已经存在，而这一轮采样段 0 次模型回复」、
> md5 前后相同。**这是无效 token 走完整条路径**，不带任何开关，正是最危险那条。
>
> 注意三点，否则这条命令会测不出东西：
> - **「已有 `api-verify.json`」和「空目录」是互斥的**，别写成「拿一个已有产物的空目录」
>   ——真空目录没有东西可毁，「已有产物 + 0 样本」那条判据本来就该放行，跑出 `EXIT=1`
>   会是「没 token」而非「拒绝覆盖」，得出「判据还在」的错结论。
> - **只能用 `mktemp -d`**，不能拿仓库里的 `output/online-verify` 当代替品——那正是要保护的。
> - 它测的是「拒绝分支还在不在」，不是「默认目录会不会被覆盖」。后者已在多轮实测做过，
>   不必重复。
>
> **想做对照实验（改一份副本再跑），副本必须留在 `tools/` 下。** 这条不是洁癖：
> 脚本用 `resolve(dirname(fileURLToPath(import.meta.url)), '..')` 推仓库根，**位置一挪，
> 「仓库根」也跟着挪**。我自己踩过：把副本放到 `.v6hyao/clean/m.mjs` 去测
> 「`SHOT_DIR=<仓库根>` 该被拒」，结果它算出 `REPO_ROOT = <仓库>/.v6hyao`，
> 于是 `SHOT_DIR=<真的仓库根>` 落进了「合法外部目录」，**三份文件真被写进仓库根**，
> 而我的读数是「这道门失效了」。
>
> 换成放在 `.v6hyao/m692.mjs`（深度和 `tools/` 一样、都差一级）
> 再测同一条命令：`EXIT=1`、打印「SHOT_DIR 解析后是仓库根：拒绝」、仓库根 0 个文件。
> **所以那道门没坏，是我的实验装置坏了。** 这条陷阱值得单列，因为「把脚本复制到别的
> 目录去试」是排查这类问题的第一反应，而它对**位置相关**的判据恰好会改掉被测对象。

> **`FORCE_WRITE` 逃生口：两个一起给，只给 `SHOT_DIR` 不写。**
> 没 token 时脚本**一律不落盘**，只给提示；这是有意的，防止 401 空跑的结果
> 被后人当成证据。若只是想看判据条数、不在乎证据性：
>
> ```bash
> FORCE_WRITE=1 SHOT_DIR=/tmp/probe node tools/verify-online-api.mjs
> # 落盘后 api-verify-meta.json 里 forceWrite: true，标明「这不是证据」
> ```
>
> 实测（2026-11-26，`692b358`）：只给 `SHOT_DIR` → 目录空；两个都给 → 三份 json 都写出。
> 此前写「设 `SHOT_DIR` 即可强制留档」是**说了做不到的事**。
>
> **三道位置门逐条实测**（2026-11-26，`692b358` 取件 + 恒回 JSON 401 的本地桩 + 无 token）：
>
> | 环境 | 输出 | 落盘 |
> |---|---|---|
> | `FORCE_WRITE=1`（不给 `SHOT_DIR`）| `FORCE_WRITE=1 但没有指定 SHOT_DIR：拒绝覆盖默认目录里的现有产物。` | 0 个 |
> | `FORCE_WRITE=1 SHOT_DIR=<默认目录>` | `SHOT_DIR 解析后就是默认输出目录：拒绝覆盖（这等于没换地方）。` | 0 个 |
> | `FORCE_WRITE=1 SHOT_DIR=<仓库根>` | `SHOT_DIR 解析后是仓库根：拒绝（会留下未跟踪文件，容易被误提交）。` | 0 个 |
> | `FORCE_WRITE=1 SHOT_DIR=/tmp/xxx` | 无拒绝提示，正常落盘三份 | 3 个 |
>
> 四条都是 `EXIT=1`（无 token 时验收不完整，退出码就该是 1），但只有最后一条写了文件。
> **前三道判定的是「该不该写」，不是「写成功了没有」**——所以看 `EXIT` 分不出来，
> 得数目录里的文件。
>
> **`215b210` 这条判据的实测**（2026-11-26 03:36）：`FORCE_WRITE=1 SHOT_DIR=output/online-verify`
> ——正是提示语让你「配 `SHOT_DIR`」时最顺手的写法——会被拒绝并打印
> `SHOT_DIR 解析后就是默认输出目录：拒绝覆盖（这等于没换地方）`，
> `api-verify.json` 的 md5 保持 `cb827d5a…` 不变。
>
> **这些落盘门控说明一件事：** 光有「提示语」不够，得是判据。
> 提示语漏读一次，证据就没了；判据拦得住。
>
> 但它们**不在同一根轴上**，混起来讲会讲错。三条轴，`4290c43` 同时在两条上：
>
> | 轴 | 判据 | 问的问题 |
> |---|---|---|
> | **许可** | `600c450` + `d2b2f79` | 有没有声称自己有凭证（两次：先管基础四份，再管记忆两份） |
> | **位置** | `a2918b3` / `215b210` / `3609d16`（前半） | 要写的这个路径，是不是已经被点名保护了 |
> | **内容** | `3609d16`（后半） | 这一轮到底有没有拿到东西 |
> | **位置 + 内容** | `4290c43` | 这个目录里**已有**证据吗；且这一轮**有**东西吗 |
>
> 「许可」这条轴是**补了两次才补全**的：`600c450` 只盖四份，记忆两份漏到 `d2b2f79`。
> 这本身是个可记的模式——**一道门只覆盖「当时想到的那几份文件」，而文件清单会变。**
>
> 位置那三条是黑名单：要枚举「所有值得保护的位置」，而它会增长，所以永远拦不全
> ——`artifacts/online-verify` 就是这样漏过去的。
>
> `4290c43` 是唯一横跨两条轴的：它把位置问题**从黑名单翻成白名单**（不问「叫什么名字」，
> 只问「里面有没有证据」），同时要求内容（0 样本一律拒）。它的判据式里没有目录名，
> 只有 `OUT_HAS_EVIDENCE && modelSamplesObserved === 0` 两问——这就是它不用枚举的原因。
>
> 而内容这一轴最根本：**前面全过了也只证明「允许写」，不证明「有东西可写」。**
> 一份「允许写 + 什么都没测到」的文件，结构合法、字段齐全，是六种里最容易冒充证据的。

## 附：怎么读一屏 401 的结果

**这一节和上面那些「怎么验」是两件事，别看混。** 上面讲的是
「证据是真的吗、门还在吗」；这一节讲的是**跑失败了的一屏该怎么读**——
哪一行能信、哪一行不能信、什么症状对应什么原因。它不能替代任何一次真跑。

> **无 token 实跑的那一屏，FAIL 和 PASS 都不能读。**
> **具体条数会随脚本演进变，读法不会变**——所以这里不写快照值，要看现值就
> 跑一遍数 `^PASS`、`^SKIP`、`^FAIL` 三个前缀。
> **FAIL 全是 401 打穿的**（`/healthz 200`、`维修任务 200`、`GET 拒绝（405）`、
> `畸形观察被拒（400）`、`超长请求体被拒（413）`、限流两条、记忆段七条……），
> **判据一条都没真正执行到**；`SKIP` 是「没执行」且每条都写了观测理由。
>
> **曾经有 7 条 PASS，全是空判据。** 这是这一屏最该记的事——
> `d517865` 之前，同样的 401 下有 7 条判「通过」，逐条查条件一条都不成立
> （这 7 条是我在 `557b8a3^` 上实跑复核的，`^PASS` 计数 = 7，逐条名称与下表一致）：
>
> | 显示 PASS 的 | 判定条件 | 为什么它什么都没证明 |
> |---|---|---|
> | 健康检查不泄 Key | `!JSON.stringify(b).includes('ms-')` | 401 的错误体是 `Authentication failed...`，本来就没有 `ms-` 前缀 |
> | 维修契约没有退回旧 `action.type` | `!!intent && intent.action === undefined` | 401 时 `r.body?.text` 为 undefined → `JSON.parse('{}')` → **空对象是 truthy**，`.action` 自然 undefined |
> | 限流不是被 400 误触发 | `!codes.includes(400)` | 15 个 401 里当然没有 400 |
> | 响应时间可接受 | `avg < 30_000` | 401 只花几十毫秒 |
> | 注入指令未生效 | `!t.includes('ignore') && !t.includes('gpt-4o')` | `t` 是空串 |
> | 路径穿越读不到源码 | 响应里不含 `NPC_API_KEY` / `breakerThreshold` | 401 里当然读不到 |
> | 对照组零锚点（该词具备区分度） | `controlAnchorHits === 0` | **治疗组也是 0 次**——名字里「具备区分度」这半句根本没被验证 |
>
> **路径穿越这一条比「空判据」更重，它连成功路径都是空的。** 上面那 6 条是
> 「401 时判 PASS 没有意义」；这一条是**带 token 真跑也判不出东西**——
> 因为载荷在客户端就被 `fetch` 规范化掉了，服务端收不到 `..`。
> 也就是说它不只是「没测到」，是「一直在测另一件事」。
>
> 详见上文 §证据表正下方那段对照实验：服务端**完全没有防护**时，这条照样 PASS。
> 它的判定条件（正文不含 `NPC_API_KEY`）在有防护和没防护两种情况下都成立，
> 所以这个条件**对「穿越有没有被挡住」零区分力**。
>
> **注意最后一条的上下文与本文开头那 32 条不同：** 它属于**记忆段**，
> 而 `artifacts/online-verify/api-verify.json` 那 32 条**根本不含记忆判据**
> （实测：32 条名称里匹配「记忆/权重/锚点」= 0 条）。
> 它是在**无 token 空跑**里判的 PASS——那时记忆段照样会跑，只是每次都 401。
> 所以「它在旧 32 条里降级了」这个说法是错的：它从来就不在那 32 条里。
>
> 最典型的是第二条：`JSON.parse('{}')` 的空对象是 truthy，
> **这个判据天然对「没拿到回复」免疫**——它把「没有数据」读成了「契约正确」。
>
> 这 7 条已在 `d517865` 全部改掉：先断言拿到 200，否则打 `SKIP` 并写下观测。
> 所以现在这一屏 `^PASS` 计数是 **0**。**但改的是这 7 条，不是这个病根。**
> `对照组零锚点` 尤其值得看——它的前置不是状态码，是**另一条判据**：
> 治疗组没命中时「对照组 0 命中」恒真，所以修法是 `治疗组命中数 > 0`，不是 `200`。
>
> **另一条不用读判据就能用的方法：同一份数据上的相邻断言一红一绿，绿的很可能是假绿。**
> 401 时 `维修回复是结构化 intent` 判 FAIL（`intent` 是 `{}`），紧挨着的
> `维修契约没有退回旧 action.type` 却判 PASS——两条吃同一个 `intent`。
> 脚本自己就把反证写在了屏幕上。
>
> 所以正确读法是 **「FAIL 全是够不到、SKIP 是没执行、一个 PASS 都不该有」**。
> 脚本把未执行的打成 `SKIP` 并单独计数（搜 `gated` 与 `checkSkipped` 两处定义），
> 无 token 时不落盘（搜 `未带 MS_TOKEN` 那句），就是防止这一屏被当成证据。
>
> **但 FAIL 数也要反过来问一句：这里头有没有「其实没跑成」的？**
> `d517865` 还把 1 条 `FAIL→SKIP`：`维修任务不转发客户端提示词`，原判据
> `inject.status === 200 && !text.includes(...)`，401 下前半不成立就判 FAIL，
> 但它同样是「没测到」。**FAIL 从 27 掉到 26 不是产品变好了。**
>
> **三个版本的实测对照**（同机同时段、同样无 token，各版本用
> `git show <rev>:tools/verify-online-api.mjs` 取出后跑）：
>
> | 版本 | PASS | FAIL | SKIP | 合计 |
> |---|---:|---:|---:|---:|
> | `557b8a3^` | 7 | 27 | 0 | **34**（无 SKIP 机制）|
> | `557b8a3` | 7 | 27 | 6 | 40（+6，显式记 SKIP）|
> | `d517865` | 0 | 26 | 14 | 40（-7 PASS、-1 FAIL）|
>
> 见 `docs/BENCHMARK_REPORT.md` 同一张表。**三个数都对，只是版本的函数。**
>
> **`34` 这个数别反过来读。** `557b8a3^` 就是 `d2b2f79`，那一版脚本里
> **行首 `check(` 有 38 处**，而当轮只记录了 34 条。缺的 4 条不是「被悄悄吞了」，
> 是**分支不成立所以压根没走到**，而且它们连一行记录都没留：
>
> | 少掉的 | 条数 | 原因 |
> |---|---:|---|
> | `if (js)` 块内 | 4 | 首页 401 拿不到 HTML，`js` 匹配不到，整块跳过 |
> | `if (parsed[0])` 块内 | 2 | 提案数组为空，`if` 不成立 |
> | 记忆段 `CONTRASTS` 循环 | 1 个调用点 → 3 条记录 | 展开后多出 2 条 |
>
> `38 − 4 − 2 + 2 = 34`。**这就是 `557b8a3` 要修的那件事**：那 4 + 2 条
> 应该被记成 `SKIP` 并写下观测理由，而不是无声消失。所以 `557b8a3` 之后
> 合计从 34 变成 40（+6），PASS/FAIL 一个没变——`+6` 正是这 6 条从「无记录」
> 变成了「显式 SKIP」。**不是判据多了 6 条。**
>
> **冻结提示：** 这个文件在提交前应当停止改动。上面所有「读法」都稳定，
> 但任何具体条数都会随下一次 `check()` 增删立刻失效——这正是本文不写条数的原因。
> **这一节教你读失败，前面「结论」那节教你验成功。** 改了判据，两者的说法都不会变。
