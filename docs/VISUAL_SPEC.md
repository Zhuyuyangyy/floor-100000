## 0. 硬约束 vs 建议（先看这一节）

改 UI 前先判断：你要动的值属于哪一类？**A 类改了会直接破版，B 类随便调。**

### A 类：硬约束（改了就破版，成本从「一行」变成「重做一屏」）

| # | 值 | 为什么是硬约束 | 破版后的症状 |
|---|---|---|---|
| A1 | 画布 **1280 × 720** | `pixelArt: true` + 整数缩放。改小会触发重采样，15 色角色变 291 色 | 像素质感消失，画面变糊 |
| A2 | `PANEL_SLICE = 28` / `PANEL_FRAME_OFFSET = -50` / `PANEL_FILL_OFFSET = -60` | Phaser 4 的 NineSlice 合成顺序把 frame 画在 fill 之上，负数偏移是唯一能让边框露出来的写法 | 所有面板变成一块纯色，边框全没 |
| A3 | `PANEL_FILL_ALPHA = 1` | 0.96 时世界道具名和 HUD 会透过来（代码注释记录了这次事故） | 面板上的字和背后的字重叠 |
| A4 | 字号 **20px 下限** | Ark Pixel 中文在这个尺寸以下无法稳定辨字；试过 16px，字只能靠上下文猜 | 字变成一坨点 |
| A5 | 文字色阶 `TEXT.primary/secondary/dim` | 对比度 15.6 / 7.7 / 5.3 : 1 是量出来的下限；`disabled` 曾是 `#5a564e`（2.7:1），导致锁定角色整行不可见 | 文字「消失」 |
| A6 | 属性板 `statWidth=148 / statPitch=188 / statX=220` | 四个板 + 金币板恰好铺满 1000px；任一值改动都会让最后一块与金币板重叠或留缝 | HUD 第二行错位 |
| A7 | 竖屏 `portraitWidth = round(720 × vw/vh)` | 由 ENVELOP 决定，不是设计值。所有竖屏坐标都必须基于它算，不能写死 | 竖屏右边被裁 |
| A8 | 触屏按钮下沿 ≤ 720 | 当前 716，只有 4px 余量。`buttonY` 再下移就出画布 | 按钮被切一半 |
| A9 | 深度契约：面板 fill = 内容 −60；`hudFeedback = 300` | 顺序反了面板内容会被自己的背景吃掉，或 HUD 提示被面板盖住 | 面板空白 / 提示消失 |
| A10 | `waitForFonts()` 必须在第一个 Scene 之前 | Phaser Text 只在创建时量一次宽度；字体晚到就永久错位 | 文字裁切、字距错乱 |
| A11 | 涨红跌绿（§2.5） | 用户明确要求，且是中国玩家默认预期 | 玩家把「加血」读成「掉血」 |

### B 类：建议值（可以调，只要保持 4 的倍数与下列区间）

| # | 项 | 当前值 | 可调范围 | 备注 |
|---|---|---|---|---|
| B1 | 背包格子间隙（桌面） | 5 | **4 或 8** | 5 不是 4 的倍数，是当前唯一的小瑕疵 |
| B2 | 数量徽标内缩 | 3 | 2–4 | 配合描边 2–3px |
| B3 | 对话选项行距 | 30 | **32** | 30 不是 4 的倍数 |
| B4 | 对话标题字号 | 30 | **24 或 26** | 30 撑不进 24px 的标题条 |
| B5 | 触屏按钮间距 | 6 | 8 | 6 偏挤，拇指容易误触 |
| B6 | 面板内边距 | 8/10/12/14/16 混用 | 统一 8 或 12 | 现状是历史遗留 |
| B7 | 世界标签字号 | 22 | 20 或 24 | 22 与 24 肉眼难辨，属于无收益分叉 |
| B8 | 家具标签是否加底板 | 无 | 建议加 `#0b0f12cc` | 与 NPC 标签统一 |
| B9 | 夜幕遮罩色 | `0x05070a`（纯黑） | 建议 `0x0a1220`（冷蓝） | 见审查 M-5 |
| B10 | 夜幕切换 | 18:00 硬阶跃 | 18–20 点线性 | 见审查 M-5 |

### 判断口径

一句话：**A 类是「不这么写就跑不起来 / 看不清」，B 类是「这么写更好看」。**
A 类值在代码里通常带 `const` 注释解释原因（`panels.ts` 的 explain 尤其完整），
B 类值大多是随手写的字面量——这正是本规范要收敛的部分。

## 1. 分辨率与像素比例

| 项 | 值 | 出处 |
|---|---|---|
| 设计画布 | **1280 × 720** | `src/core/design.ts` `DESIGN_WIDTH/HEIGHT` |
| 宽高比 | 16:9 | 同上 |
| 像素渲染 | `pixelArt: true`、`antialias: false`、`roundPixels: true` | `src/core/gameConfig.ts` |
| 画布背景 | `#0b0f12` | `gameConfig.ts` `backgroundColor` |
| 横屏缩放 | `Phaser.Scale.FIT` + `NO_CENTER` | `gameConfig.ts` |
| 竖屏缩放 | `Phaser.Scale.ENVELOP`，取中间竖条 | `gameConfig.ts` + `design.ts` `portraitViewportFor` |
| 参考窗口 | 1280 × 800（E2E 与截图基线） | `playwright*.config.ts` |
| 竖屏参考 | 390 × 844（iPhone 14） | `e2e-audit/visual-audit.spec.ts` |

### 关键推论：1 设计像素 ≈ 1 屏幕像素

1280 宽的窗口显示 1280 宽的画布，比例是 **1:1**。所以：

- `fontSize: '24px'` 就是 24 个屏幕像素高，**不是** 12px 的两倍。
- 想「放大一点」就 +4，不要 +1。

> ✅ **文档分歧已修（2026-11-26）**：`docs/05_ART_GUIDE.md:9` 与
> `docs/02_TECH_SPEC.md:67` 原写「内部渲染分辨率 640x360」，现已改为
> **1280x720** 并附上演变理由与派生结论清单。`uiKit.ts:43` 的注释仍残留
> 这个数字，登记为 `docs/UI_AUDIT_R3.md` D-6，**待修、不归本文档作者**
> （在 `src/` 里，`src/` 除 `visualTokens.ts` 外先问 team-lead）。
>
> 为什么从 640x360 改成 1280x720：塔楼剖面要在 16:9 里同时看到 3.6 层，
> 用 640x360 需要 zoom 0.5，而 zoom 0.5 会让渲染器重新采样，15 色的角色
> 变成 291 色（`src/core/design.ts:1-16`）。**以 1280x720 为准。**
>
> ⚠ **同一处地基错误还有第三个受害者，而且它在跑起来的代码里**：
> `src/systems/TowerNav.ts:30` 的 `VIEW_H = 360` 是 640×360 时代的值，
> 相机实际高 720。后果是塔楼总览的 100 条楼层带只画在 `y=36..336`，
> **700px 高的画布下半部整片空着**（截图 `e2e/screenshots/20-tower-overview.png`）。
> 这是「100000 层」这个核心概念唯一的产品呈现，登记为 D-10，待修。

### 竖屏的可见宽度不是 1280

竖屏下用 ENVELOP，画布被裁成一条竖条：

```
portraitWidth = min(1280, round(720 * viewportW / viewportH))
```

390×844 时 = `round(720 * 390/844)` = **333**。所有 `setScrollFactor(0)` 的
HUD/面板都按 333 宽布局，不是 1280。这是竖屏 UI 全部问题的根源——
很多坐标是按 1280 写的，靠 `fitHudLine` 截断兜底。

### 2.5 数值增减色：**涨红跌绿**（用户明确要求，硬约束）

> 这是**用户点名的中国习惯**，不要按欧美惯例（欧美是涨绿跌红）写。

凡是「屏幕上的数字刚刚变大/变小」的表达，一律：

| 方向 | 颜色 | 用哪个令牌 | 说明 |
|---|---|---|---|
| **涨**（增加 / 回复 / 收益） | **红** | `TEXT.warn` `#e8907c` 或 `STAT_COLOR.hp` 系 | 暖红。`#e8907c` 偏珊瑚，在深色底上不会与「危险」混淆，但它确实是红 |
| **跌**（减少 / 损失 / 扣款） | **绿** | `PALETTE.clothHigh` `#77c6a4` | 青绿 |
| 中性（无变化 / 持平） | 不变色 | `TEXT.primary` | — |

**当前实现状况（实测，见 `UI_AUDIT_R3.md` M-7）**：

仓库里**没有任何「变化量浮字」**——没有 `+30` 从角色头上飘起来这种东西。
唯一的数值增减表达是底部一条 `feedbackText`，而且**涨跌同色**：

```
用到 的 8 处 flash() 里，带数值的只有 2 处：
  GameScene.ts:3201  `建造了 X（-2 分钟）`         ← 时间损失，仍是暖橙
  GameScene.ts:4556  `使用 净水 · 水分 +30`         ← 属性收益，也是暖橙
两处都走 PALETTE.lightHigh `#f4b66a`，涨跌不分。
```

**所以这条规则现在是「已定义、未实现」**。等哪天做浮动数值（大概率要做，
它是让玩家感知「这一口水值多少」的最直接手段），必须按上表落色，
不要照抄欧美 demo 的绿色 `+HP`。

## 3. 字体与字号阶梯

### 3.1 字族

来源：`uiKit.ts` `FONT_FAMILY` + `index.html` 的两个 `@font-face`。

```
'ArkPixel Latin', 'ArkPixel ZH', 'Microsoft YaHei', 'PingFang SC', 'Noto Sans CJK SC', sans-serif
```

- Ark Pixel 10px **等宽**像素字，拉丁与简体中文分成两个 woff2（共 136KB），
  靠 fallback 链解析缺字。
- **必须**在创建第一个 Text 前加载完：`src/main.ts` `waitForFonts()` 会
  `document.fonts.load` 两个 face（3s 超时兜底）。否则 Phaser 量到的是
  回退字体的宽度，字体换上来后不会重新排版 → 裁字 / 错位。

### 3.2 字号阶梯（当前实际值）

来源：`uiKit.ts` `TYPE`。

| 令牌 | 值 | 用途 |
|---|---|---|
| `title` | **30px** | 面板标题 |
| `body` | **24px** | 正文、物品详情、对话正文 |
| `caption` | **20px** | 说明、HUD 次要行、**最小合法中文** |

**20px 是硬下限**。原因：1280x720 下 1:1 显示，20px 的中文已经是这个像素字
能稳定辨字的最小号；16px 的汉字只能靠上下文猜。

### 3.3 阶梯之外实际在用的字号（技术债）

**口径要说清楚，否则数字对不上**：
`grep -rn "fontSize" src/ --include="*.ts" | wc -l` = **109 处**（全 `src/`，
不含测试文件里没有 fontSize）。其中 `GameScene.ts` 一个文件占 **63 处**。

- 走 `TYPE.*` / `TEXT_SIZE.*` 常量：**53 处**
- 硬编码字面量（`fontSize: '22px'`）：**24 处**
- 三元里的竖屏分支（`fontSize: \`${mobile ? 13 : TYPE.caption}px\``）：其余

硬编码的档位分布（`grep -o` 计数）：

```
22(8)  20(4)  36(2)  32(2)  26(2)  24(2)  52(1)  18(1)  14(1)  13(1)
```

最高频的「非阶梯值」仍是 **22px（8 次）**——世界层标签（家具名、NPC 名、容器名）
全用它。它与 24 在画面上肉眼难辨，属于无收益的分叉。

> `src/ui/visualTokens.ts:104` 的注释写「GameScene.ts 内有 63 处 fontSize」，
> 这个数字**是准的**（实测 63），但它只是全仓 109 处的一部分，引用时别混用。

**冻结规则（v1.0 起）**

1. 新增 UI 只允许 `20 / 24 / 26 / 30` 四档（26 是「大正文」，用于按钮与对话）。
2. 已存在的 `22` 视为世界层标签专用，**不再增加新用途**。
3. `12 / 13 / 14 / 18` 只允许出现在竖屏分支里（`portraitMode ? 13 : TYPE.caption`
   这种写法），因为 333px 宽的竖条放不下 20px 的 14 字行。
4. `36 / 46 / 52` 只允许出现在标题页与结算页。

## 4. 间距、圆角、描边

### 4.1 网格单位

来源：`uiKit.ts` `UI_UNIT = 4`。

所有 padding / gap / 行距**必须是 4 的倍数**。当前违反的：

| 位置 | 现值 | 应为 |
|---|---|---|
| 背包格子间隙 | 5 | 4 或 8 |
| 对话框选项行距 | 30 | 32 |
| 世界标签 y 偏移 | -8 / -68 / -104 / -108 | 4 的倍数（-8、-68 合规；-104、-108 合规） |
| 面板内边距 | 8/10/12/14/16 混用 | 统一 8 或 12 |

### 4.2 圆角

**一律 0。** 像素风不做圆角，`panels.ts` 明确写了旧实现的
`strokeRoundedRect` 的「soft anti-aliased corners broke the pixel look」，
已换成 8 片 Image 拼的直角边框。**不要再用 `strokeRoundedRect`。**

### 4.3 面板描边

来源：`panels.ts`。

| 项 | 值 |
|---|---|
| 边框切片 `PANEL_SLICE` | **28px**（来自美术包的铆钉金属板角件） |
| 描边宽度 | 1px |
| 填充带数 `FILL_BANDS` | **5**（从 `#1b2731` 渐变到 `#090d10`，alpha 1） |
| 填充 alpha | **1.0**（不是 0.96，原因见 §9） |

### 4.4 推荐间距刻度（新增，`visualTokens.ts` `SPACE`）

| 令牌 | 值 | 用途 |
|---|---|---|
| `xs` | 4 | 行内微间距 |
| `sm` | 8 | 元素内边距 |
| `md` | 12 | 面板内边距（推荐） |
| `lg` | 16 | 区块间距 |
| `xl` | 24 | 面板标题条高 |
| `xxl` | 32 | 面板之间的呼吸 |

## 5. 组件尺寸

### 5.1 HUD

#### 对话框高度是算出来的，不是选的（`[硬约束]`）

这是本规范里唯一一条「面板尺寸由文字决定」的规则，改任何一项都会连锁。

```
wrapWidth   = panelWidth − 44
hanPerLine  = floor(wrapWidth / TYPE.body)          // 24px 汉字，实测 1:1
messageLines= ceil(MAX_UTTERANCE / hanPerLine)      // MAX_UTTERANCE = 60
wellHeight  = messageLines × 25 + 8                 // 25px = 24px 汉字的实测行高
wellBottom  = 28 + wellHeight
optionsTop  = wellBottom + 12
panelHeight = optionsTop + 4 × 30 + 40
```

| | 桌面 460 | 竖屏 309 |
|---|---|---|
| wrapWidth | 416 | 265 |
| Han / 行 | 17 | 11 |
| 行数 | **4** | **6** |
| 正文井高 | 108 | 158 |
| 面板高 | **308** | **358** |

竖屏两条都是实测过的：`dialogue-fit-probe.spec.ts` 在 390×844 视口灌 60 字，
量到正文 `264x150 y[213..363]`、底板 `y[209..367] h=158`（= 6 行 × 25 + 8），
选项 0 在 `y[379..404]`，0 交叠。

> 注意 `dialogueLayout.test.ts` 里 `PORTRAIT_PANEL_W = 265` 是**更窄的保守**场景
> （`panelWidth` 265 → `wrap` 221 → 9 字/行 → 7 行 → 面板 383），用来证明
> 「行数不再被 6 行封顶」。真实竖屏 `panelWidthFor(460)` 得到 309，是 6 行。
> 两个数字都对，说的是不同输入。

**为什么不能用「最多 6 行」这种封顶**：竖屏是 9 字/行，60 字要 7 行。
旧实现写死 `MAX_LINES = 6`，第 7 行被截到选项行上（实测多出 25px）。
现在行数完全由 `MAX_UTTERANCE` 推出，台词上限放宽一倍面板自动长高
（`dialogueLayout.test.ts` 用 120 字反证过）。

**这条的连锁表**（任何一项变，下面全变）：

| 改动 | 后果 |
|---|---|
| `TYPE.body` 变大 | 每行字数变少 → 行数变多 → 面板变高 |
| `MAX_UTTERANCE` 变大 | 行数变多 → 面板变高（测试会先红） |
| 面板宽变窄 | 每行字数变少 → 行数变多 → 面板变高 |
| 正文两侧内边距 ≠ 44 | `contentInset` 参数，必须一起改 |

**正文是顶部锚定在井心的**（`setOrigin(0.5)` + `y = WELL_TOP + WELL_H/2`），
不是「固定 y + 居中」。后者会让 1 行短句和 7 行长句向上下两侧同时生长，
长句的上半截顶穿标题条——这是 `bac96ae` 只开 advancedWrap 时实测出的
次生缺陷（21px 压在选项上、33px 出井）。

## 10. 修改 UI 的检查清单

改任何 UI 前过一遍：

1. **颜色**：是不是只用了 `ROLE` / `UI` 里的语义角色？有没有引入第 17 色？
2. **字号**：是否在 `20 / 24 / 26 / 30` 四档里？竖屏例外是否写了 `portraitMode ?`？
3. **间距**：是否 4 的倍数？
4. **换行**：需要折行的中文 Text 有没有 `useAdvancedWrap: true`？
   这不是「排版偏好」，是中文能不能折行的唯一开关——`basicWordWrap` 按空格切词，
   中文整句只有一个词，而「词比整行宽」的分支守卫是 `if (j > 0)`，首词时不成立，
   于是零折行。**当前 14 处 `wordWrap`、只有 3 处开了 advanced**，
   剩下的只要被喂进超宽中文就必横向溢出（实测 `invDetailBody` 跑出面板 238px）。
5. **对比度**：文字色不低于 `TEXT.disabled`（4.6:1）？
6. **深度**：新元素属于 §7 的哪一层？会不会盖住 `hudFeedback(300)` 或
   被面板 fill 吞掉（−60）？
7. **竖屏**：`portraitWidth` 只有 ~333，不是 1280。所有 `x = DESIGN_WIDTH - N`
   的右对齐元素在竖屏下会跑出屏幕。
8. **HUD 遮挡**：世界层标签会不会滑进 y < 124 的不透明带？
   （跑 `e2e-audit/hud-band-probe.spec.ts`）
9. **面板溢出**：面板内容是否超出 `panelW - 24`？跑 `e2e-audit/wrap-probe.spec.ts`。
10. **截图**：改完跑
    `npx playwright test -c playwright.audit.config.ts --workers=1`，
    然后**真的看**那 19 张图。这是本文档存在的理由。
