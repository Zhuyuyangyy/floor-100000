## 一、别人怎么做的（四条会改变结果的结论）

### 1. 调色板是纪律，不是偏好

成熟像素项目几乎都用**受限调色板**（16–32 色），代表是 Lospec 上的 Endesga-32 / Apollo / Sweetie-16。
原因不是风格，是**可读性**：色数少 → 每个色位都必须承担明确的明度角色，画面自然分出层次；
色数多 → 颜色互相靠得太近，缩到小尺寸就糊成一片。

本项目现状：程序化美术各自用各自的颜色，`pixelArt.ts` 的 COLOR 六色、`walkcycle.ts` 每人 12 色、
`uiKit.ts` 又一套、`lighting.ts` 再来一套。**四套调色板互相不认识**，这是"简陋感"的主要来源。

### 2. 角色先做剪影，再做明度，最后加细节

通行流程：**剪影 → 三阶明度（暗/中/亮）→ 细节 → 描边**。
- 剪影阶段：整块填一个颜色，缩到 1x 看还能不能认出是个人、在做什么动作
- 三阶明度：每个材质最多 3 个明度值，不许更多
- 描边：1px，颜色接近但明显暗于主体（不是纯黑）

本项目现状：角色直接画细节，没有剪影阶段；躯干用两步明暗但腿/臂只有单色。

### 3. 角色必须和背景**明度分离**

最常见的"角色看不清"不是颜色问题，是**明度和背景撞了**。
规则：角色主体明度要落在背景明度**之外**的区间，或者用一圈比背景更暗的描边把轮廓锁住。
本项目现状：墙 ~48 亮度、角色衣服在暗处被洗到 ~40。**撞了**。

### 4. 光照分两遍：压暗（multiply）+ 提亮（add）

- 环境/阴影用**压暗**（把整体乘暗），
- 光源用**加亮**（ADD），
- 关键是**两者要分开**，且光源要盖在角色之上，角色才有"被照到"的感觉。

本项目现状：ADD 光已做对（`addGlow`），压暗层刚做对（depth 0）。**这一步算完成**。

## 三、量化验收方法（每轮都要跑）

脚本 `tools/art-audit.mjs`（待建）输出：

- `contrast(角色, 背景)` — 角色区域 vs 身后墙面的明度差
- `paletteSpread` — 全图 distinct 色数 / 主色占比
- `brightShare` — 亮部像素占比（目标 8–20%）
- `verticalProfile` — 竖向明度剖面（要有起伏，不能平）

**通过标准**：角色对比 ≥25、主色占比 ≤20%、亮部 8–20%、剖面方差 ≥12。

## 三之一、参照数据（实测，用于校准阈值）

用同一套算法测出来的边缘密度（相邻游戏像素明度跳变 >16 的占比）：

| 参照 | 边缘密度 |
|---|---|
| CENTUM 图块集 tileSpritesheet | **13.3%** |
| CENTUM 怪物图集 | 8.2% |
| CENTUM 物品图集 | 3.2% |
| 负责人给的写实渲染图（标题） | 2.7% |
| 负责人给的写实渲染图（楼层） | 1.8% |
| **本项目楼层（实测）** | **5.5%** |

结论：
1. **一幅"场景"天然比图块集稀疏**——不能拿图块集的 13% 当场景目标
2. **写实渲染图的边缘密度反而最低**（2-3%），因为它靠柔和渐变；像素画靠硬边
3. 本项目 5.5% 落在真实像素艺术的区间中段，**比写实参考图更"密"**
4. 因此密度门槛定为 **≥4%**，不是最初凭空的 8%

## 三之二、被证伪的三个指标（重要）

| 原指标 | 为什么错 | 改成 |
|---|---|---|
| 亮部占比 8–20% | 那是白天场景的数。夜场景实测 2–6% 才是对的 | ≥1.5%，注释写明"夜里就该这么多" |
| 竖向剖面 stdev ≥8（按 8 条横带均值算） | **会惩罚好画**：天花板加亮灯后顶带和中带变接近，数值反而下降。横带均值量的是带对齐，不是结构 | 改成**全画面逐像素明度 stdev ≥22**（实测 23.5），且采样区排除 HUD/底栏 |
| 边缘密度 ≥8% | 拿图块集的数当场景目标。实测场景 5.5% 已高于写实参考图 | **≥4%**，参照表见三之一 |

教训：**三个阈值全是凭空的，全部偏严**。任何没经过实测的阈值都是迷信，改了要写清推导。
