## 0. 这份报告要回答什么

判断这个 AI NPC 系统是否成立，需要分别回答四个问题。它们**互相独立**，
一个通过了不代表另一个通过：

| # | 问题 | 为什么单独问 |
|---|---|---|
| Q1 | 模型能不能**说人话**？ | 传输层完整性。空正文、截断、思维链泄漏都在这里暴露 |
| Q2 | 模型提的动作**合不合法**？ | 契约遵守度。合法但无意义 vs 非法但有信息量，是两种失败 |
| Q3 | 系统能不能**完成一件事**？ | 端到端有效性。提案合法 ≠ 玩家达成目标 |
| Q4 | **规则层**有没有真的拦住非法动作？ | 这是本作品的核心主张。若拦截率不是 100%，整个架构主张就站不住 |

**Q4 的分母不是模型的失败次数，而是所有非法提案数。** 一个"从来没被拒绝过"的
系统可能只是模型从没试过越界——那证明不了规则有效。

### 2.2 Q2 动作被接受率 / 非法动作拦截率

| 指标 | 定义 | 值 | 来源 |
|---|---|---:|---|
| 动作被接受率 | 模型提案通过 Validator 的比例 | 【待实测】 | 需在真机跑多场景，读 `competitionTrace` |

**关于"拦截率必须 100%"：** 这不是"希望达到"的目标，而是**架构不变量**。
`competitionRules.validateProposal()` 是唯一的准入关口，执行器只在
`validation.accepted === true` 时被调用。若测出拦截率 < 100%，说明存在绕过路径，
那是缺陷而不是"性能指标"。

单元测试层面已有覆盖（`src/ai/competitionExecutor.test.ts`、`src/ai/rulesExecutor.test.ts`、
`src/scenarios/socialNpcDemo.test.ts` 各自断言了 `validateProposal` 的拒绝路径），
但那证明的是"已知的非法输入被拒"，不是"任意模型输出都不会穿透"。
后者只能靠真实模型的多轮采样逼近。

> 注意：`src/ai/competitionRules.ts` **没有**独立的 `competitionRules.test.ts`。
> 它的拒绝分支是被上述文件间接覆盖的。这是一个测试组织上的薄弱点——
> 若要做"拦截率"统计，建议先补一个按原因枚举逐条断言的测试文件。

> **为什么不是「40 项全过」——两条 FAIL 各自的账：**
>
> **① 第 40 条「路径穿越读不到源码」：判据假阳性，产品没有泄漏。**
> 线上把 `/../server/npc-proxy.mjs` 原样发上去（`node:http` 的 `request({ path })`），
> 拿到的是 **HTTP 400、225B、`server: Tengine`** 的**网关错误页**：
> `<!DOCTYPE HTML PUBLIC "-//IETF//DTD HTML 2.0//EN"> … <title>400 Bad Request</title> … Powered by Tengine`。
> 逐字查过：**不含 `NPC_API_KEY`、不含 `/api/npc/decide`、不含任何仓库源码**。
> 判据判 FAIL 是因为它只比「与基线不同」：基线那次拿到 200 的首页（1668B），
> 载荷这次拿到 400 的错误页，两个不同 → 被读成「命中源码」。
> 这条判据**本来就被记过「无法被反例推翻」**（拿无防护静态服务器对跑照样 PASS），
> 现在它从另一头坏了：**任何差异——包括两个不同的错误页——都会被读成泄漏。**
> 正确的判据应当是「载荷响应里出现了源码内容」，不是「与基线不同」。
>
> **② weight 专项「记忆权重影响决策」：本轮已绿（改的是产品与输入，不是判据）。**
> 实测 `base{gift:4}` 极性 +1.00、`pos{gift:4}` +1.00、`neg{refuse:3, gift:1}` −0.50
> → 差 **1.50** ≥ 1.00，单调性成立。绿的原因有两条**产品侧**的：
> **weight 渲染原来是不对称的**（只有负向两档明说「负面」，正向两档只说「重」，
> 模型只学得到「负面 → 戒备」一个方向）→ 正向两档补性质词 `·恩情`、负向补 `·记恨`；
> **正向动作本来不可达**（观察无库存 → `gift/trade` 违反「不得声称拥有你没有的物品」，
> 正向极性无从表达）→ 给观察补了一件 NPC 真有的物品（保险丝 ×1）。
> 判据的阈值、样本数、单调性、采样完整性判据一律没动，判据名与调用点也未变。
> ⚠️ **口径**：本轮差异**全部来自负向档**（负向让模型 3/4 转 `refuse`），
> 正向档与中性档没有可观测差异（都是 `gift`——那句 summary 本身就是一次帮助）。
> 所以它证明的是「**weight 的负面档能把态度从回报推向戒备**」，不是「双向驱动」。
>
> **判据能证伪什么，四档实测过（载荷固定 `/../server/npc-proxy.mjs`、`rawGet` 直发）：**
> 线上原样 → PASS；**只删越界比对、保留 `normalize` → 仍 PASS**；只删 `normalize` →
> 403/SKIP；两道都删 → **FAIL（47B 含源码）**。第二格是关键：`safePath` 有两道防线，
> `normalize()` 已经先把前导 `..` 吃掉，所以这条判据证伪的是「能被 `/../` 读出 dist 外
> 的源码」，**不是**「越界比对那一行还在」。**现在线上是第三种状态：网关直接 400。**

> ⚠️ **另有一条不在 40 项里的问题，比路径穿越更严重：畸形 URL 能把服务打死。**

### 第一次：2026-11-26 11:07，记忆段 **6 FAIL / 1 SKIP / 1 PASS**

走公开地址（基础段 32 条全 PASS），记忆段全红：

| 判据 | 结果 | 实测 |
|---|---|---|
| 记忆改变决策：无记忆 vs 受助 | FAIL | 两侧各 4~5 次采样全是 `dialogue`，极性差 0.00（需 ≥1.00），锚点未命中 |
| 记忆改变决策：失约 vs 守约 | FAIL | 同上，极性差 0.00 |
| 记忆改变决策：被拒 vs 获赠 | FAIL | 同上，极性差 0.00 |
| 记忆改变决策（三组合一） | FAIL | 3 组全成立=false，极性总增益 0.00（需 ≥1.50） |
| 记忆组出现锚点回响 | FAIL | 命中 0 次——锚点词「银色绝缘胶带」一次都没被复述 |
| 对照组零锚点（该词具备区分度） | SKIP | 治疗组也没命中，无法证明该词有区分度 |
| 记忆权重影响决策（同文本只翻 weight） | FAIL | base/pos/neg 全是 `dialogue`，极性差 0.00；且 neg 段采样失败 1 次，样本不全 |
| 采样噪声基线（同记忆同参数） | PASS | intent 相同、text 不同 |

**根因不是接线。** 代理侧已实测：`server/npc-proxy.mjs` 的 `buildMessages` 确实把
`第2天 help［较重］：…` 渲染进提示词（本地代理 + 假上游的请求日志逐字可查），
`weight` 强度词也在。**模型读到了记忆，却没有因此换动作**——
`availableActions` 给了 `dialogue/gift/refuse`，它十来次采样全选 `dialogue`。

**但记忆确实改了它说的话**（同一屏的观测备注里有原文对照）：

- 失约 vs 守约——对照：「昨天你说会带保险丝回来，可我等了一整夜都没见到你…」；
  记忆：「谢谢你昨天一早把保险丝送到，我记着这份情…」
- 被拒 vs 获赠——对照：「我知道上次你拒绝把木板借给我…」；
  记忆：「是你。那天你把最后一块木板给了我，我记着…」

**根因定位到提示词：** 记忆只有一行「相关记忆：…」，从没被告知**它该影响选择**。
「记住了」和「记住了并据此改变」在模型眼里没有区别。

### 修法：改产品，不改判据

`server/npc-proxy.mjs` 的 `buildMessages` 增加一段「记忆决策」契约——
记忆必须影响选择（玩家帮过你 → 倾向回报；玩家失约/伤害过你 → 倾向戒备），
但**仍然只能从「可用行动」里选，规则层照样能否决**。另加一条守护测试：
**有记忆才写这段、无记忆不写**（否则是在教模型编造记忆）。
判据一条没动，阈值一条没动。

标成 +0.9 也不会让模型更想付出，它读的是文本。
`weight` 强度词在提示词里逐字可查（`极重/较重/一般/偏负面/严重负面`）。

### 第三次：2026-11-26 16:58，再修两处后重跑，记忆段 **8 条全绿**

这一轮改了两处**产品**、一处**输入**，判据阈值一条没动：

1. **weight 渲染不对称 → 对称**（`server/npc-proxy.mjs` 与 `src/ai/prompt.ts` 两份同步）：
   旧映射只有负向两档明说「负面」（偏负面/严重负面），正向两档只说「重」
   （极重/较重），**不带褒贬**——提示词里「守约」（+0.5）与「未决」（0）只差在分量上，
   而「毁约」（-0.6）明写着负面。模型只学得到「负面 → 戒备」一个方向。
   正向两档补性质词：`极重·恩情 / 较重·恩情 / 一般 / 偏负面·记恨 / 严重负面·记恨`
   （「恩情/记恨」对得上产品真正产出的记忆种类：守约 +0.5、获赠 +0.4/+0.6 是恩情；
   毁约 -0.6、被拒/欠债 -0.2/-0.6 是记恨；事实类 0 是一般）。

> 应用在门户 iframe 里完整启动（Menu 场景、1280×720 画布），同源代理返回

> `studio-…api-inference.modelscope.net`——那是平台设计（该地址必须带 SDK token），
> 不是空间私有。

> **「无 token 实跑」那一屏不能当验收读。** 读法固定，数字不固定——别抄下面的值，
> 自己跑一遍数 `^PASS` / `^SKIP` / `^FAIL` 三个前缀
> （`d517865`，2026-11-26 03:30 实测：40 条里 26 FAIL / 14 SKIP / **0 PASS**）。
> **FAIL 没有一条反映产品行为**——全是 401 打穿的
> （`/healthz 200`、`维修任务 200`、`GET 拒绝（405）`、`畸形观察被拒（400）`、
> `超长请求体被拒（413）`、限流两条、记忆段七条……）。判据一条都没真正执行到。
>
> **这一屏最该记的不是 FAIL 多，是「PASS 曾经有 7 条」。** 早期版本在同样的 401 下
> 判了 7 条 PASS，逐条查判定条件，一条有效的都没有：
>
> - `健康检查不泄 Key` 查的是 `!JSON.stringify(b).includes('ms-')`，而 401 的错误体
>   是 `Authentication failed...`，本来就没有 `ms-` 前缀
> - `维修契约没有退回旧 action.type` 靠 `!!intent`，而 401 时 `JSON.parse('{}')`
>   的空对象是 truthy——**它把「没拿到回复」读成了「契约正确」**
> - `限流不是被 400 误触发` 靠「没有 400」，15 个 401 里当然没有
> - `响应时间可接受` 靠 `avg < 30000`，401 只花几十毫秒
> - `注入指令未生效` 查的是一个空串
> - `路径穿越读不到源码` 查的是 401 页面
> - `对照组零锚点（该词具备区分度）` ——**治疗组同样 0 次命中**，
>   名字里「具备区分度」那半句根本没验证
>
> 这 7 条已改成「先断言拿到 200，否则打 `SKIP` 并写明观测」（`d517865`），
> 所以现在那一屏是 0 PASS。**但修的是这 7 条，不是这个病根。**
> 其中 `对照组零锚点` 的修法值得单说：它的问题不是缺状态码前置，
> 而是**它的前提是另一条判据**——治疗组没命中时，「对照组 0 命中」恒真。
> 所以正确的修法是 `治疗组命中数 > 0`，不是 `status === 200`。
>
> 还有一条方法：**同一份数据上的相邻断言，一条红一条绿，绿的那条很可能是假绿。**
> 401 时 `维修回复是结构化 intent` 判 FAIL（`intent` 是空对象），紧挨着的
> `维修契约没有退回旧 action.type` 却判 PASS——两条吃同一个 `intent`。
> 不用分析判据写法就能看出后者有问题。
>
> 所有「通过/不通过」的判据都可能犯这个错，只要它写的是「没有出现坏东西」
> 而不是「观察到了好东西」。**判据应当首先断言「拿到了 200」。**
> 脚本把未执行的单独打 `SKIP` 并计数（末行 `其中 N 条未执行，非产品不合格`），
> 无 token 时不落盘（搜 `未带 MS_TOKEN` 那句），就是为了不让这种屏幕变成「证据」。
>
> **总条数和 FAIL 数都变过，三次都是我亲手跑的**（同机、同时段、同样无 token，
> `FORCE_WRITE=1 SHOT_DIR=/tmp/...`；`git show <rev>:tools/... > /tmp/x.mjs` 取出各版本，
> 用 `^PASS` / `^FAIL` / `^SKIP` 三个前缀数）：
>
> | 版本 | PASS | FAIL | SKIP | 合计 | 这一版改了什么 |
> |---|---:|---:|---:|---:|---|
> | `557b8a3^` | 7 | 27 | **0** | **34** | 还没有 SKIP 机制，未执行的不进清单 |
> | `557b8a3` | 7 | 27 | 6 | 40 | 6 条「整段 `if` 不成立就消失」改成显式记 SKIP（**+6，总数 34→40**） |

>
> **这三行放在一起说明的不是「数字不准」，而是「数字只是脚本的版本号」。**
> 所以正文任何一处写具体条数，都必须带版本号——不带就是错的。
>
> 顺带一条容易误读的：`d517865` 的 FAIL 从 27 掉到 26，**不是产品变好了**，

## 5. 如何填这张表（给后来者）

1. **先固定 §1 环境**，否则后面所有数字都不可比。
2. **每次 run 存原始记录**，不要只存汇总：
   - 真机推理：`node tools/spark-run-record.mjs`（自动写到 `artifacts/spark-runs/`）
   - 线上验收：`node tools/verify-online-api.mjs`
     （默认输出到 `<repo>/output/online-verify/`，按脚本自身位置定位、与 cwd 无关；
     **无 `MS_TOKEN` 时一律不落盘**，设了 `SHOT_DIR` 也不写——要看条数就
     `FORCE_WRITE=1 SHOT_DIR=/tmp/probe` 两个一起给，落盘后 meta 里 `forceWrite: true`；
     **目标目录里已有 `api-verify.json` 时，0 样本一律拒绝覆盖**（`4290c43`）——
     这条不看有没有 token，也不在 `FORCE_WRITE` 分支里；
     `output/` 被 `.gitignore` 忽略，要留档就复制到已跟踪的 `artifacts/online-verify/`——
     仓库里现有的那份就是这么来的）
   - 离线基准：`npm run competition:benchmark`（写到 `artifacts/benchmark/`）

   > **引用证据时认准 `artifacts/`，不要引 `output/`。** 后者不在版本库里
   > （评委 clone 后不存在），且会被本地空跑覆盖成「文件名是证据、内容零样本」的文件。

   **验证脚本的断言条数要现算，不要抄。** 这个文件在赛前被反复重写
   （同一晚记忆段从 7 条变到 8 条，判据从「逐组断言」改成「逐组 + 聚合」），
   任何写死的条数和行号隔一次提交就失效。按段落标题定位：

   ```bash
   node -e "const L=require('fs').readFileSync('tools/verify-online-api.mjs','utf8').split('\n');let f=0,r=[];for(let i=0;i<L.length;i++){if(/2\.6 记忆影响决策/.test(L[i]))f=1;if(f&&/── 3\. 真实模型决策/.test(L[i]))break;if(f&&/^\s*(check|checkIfMeasured|checkSkipped)\(/.test(L[i]))r.push({n:i+1,ind:(L[i].match(/^\s*/)||[''])[0].length});}console.log(r.map(x=>x.n+'@'+x.ind).join(' '));console.log('条数 =',r.reduce((s,x)=>s+(x.ind>=6?3:1),0));"
   # 必须数三类函数名：check( / checkIfMeasured( / checkSkipped(。
   # 只匹配 check( 会漏掉「先断言前提、否则 SKIP」那几条——
   # 自检：**记忆段内**静态条数应等于该段运行时 ^PASS+^FAIL+^SKIP 的行数。
   # 此等式只在记忆段成立——全局有互斥分支（if/else 各写一份 check），
   # 静态调用点 47 而运行时 40 是正常的，别拿全局去校验。
   ```
3. **每个数字必须能指到一个文件**。指不到的写 `【待实测】`。
   对会变动的代码结构（脚本条数、行号），指向一条**能重跑出这个数的命令**，
   而不是一个快照值——写死的行号隔一次提交就会失效。
4. **样本量写在数字旁边**。`100%` 和 `100% (N=6)` 是完全不同的两个声明。
5. **不要跨环境合并数字**。直连和代理的延迟不能平均。
6. **能重跑的才算结论，数出来的只能算线索。**
   如果一个结论是靠数代码里某个字符串出现了几次得出的，它只能证明「那个字符串还在」。
   要证明判据生效、要证明模型被调了几次，**只能跑**。

   **一条可复现的假结论**（用只让限流段成功的桩跑同一份验收脚本——同一屏的上半部与下半部互相打脸）：

   ```text
   PASS 限流前先有成功请求 :: 序列 200×15
   ...
   目标 …｜本轮 0 次模型回复：token 无效…
   ```

   上半部说有 15 次成功，下半部说本轮 0 次模型回复。**两条都是真的**，
   合起来只能证明一件事：那 15 次成功**没走到模型**。
   限流段成功只证明「限流之前先有成功请求」这条判据成立，
   **推不出「模型被调用过」**——判据读的是哪一段，就只证明哪一段。

   同一份数据上，一条判据说「有」、另一条说「没有」，先怀疑后者在自证：
   **一条能复现的假结论 + 一条判断标准**留下来的价值，
   远大于「我们审出了 N 处瑕疵」——条数会被下次复核推翻，方法论不会。
