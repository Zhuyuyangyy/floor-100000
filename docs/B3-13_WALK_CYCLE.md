# B3-13 侧面行走循环：角色终于会走路

负责人反馈「你这个就是个纸片人在那里动」。本文件记录根因、实现与实测。

## 1. 根因不是「没有动画帧」，是朝向错了

上一轮（B3-12）我说过「需要你给行走帧」。**这个诊断不完整。**

真正的根因：**美术是正面朝向，游戏是侧视横卷轴。**

| 证据 | 方法 | 结果 |
|---|---|---|
| 脸在画面水平中心 | 逐色 ASCII 图 + 肤色质心 | `char-xiaozhou` 最亮像素在 (32, 15)，即 64×96 画布正中心 |
| 不对称来自配件而非朝向 | 镜像不对称度 | 30.2 / 33.4 / 35.5 / 46.3，但挎包、肩带、口袋都是单侧配件 |

一个正面朝向的角色横向移动，观感就是一张卡片在滑。**所有 2D 横版游戏用侧面或四分之三侧面，就是为了避开这个。** 侧面视角下腿的摆动直接构成「在走」，不需要额外解释；正面视角下没有任何位移量的代码能把它变成走路。

所以 B3-12 那个 2px 的 bob 是**给滑动上妆**。方向错了。本轮把它删掉（`bobOffsetPx` / `advanceBobPhase` 及 6 条测试一并移除，动画接管全部垂直运动）。

## 2. 实现：逆运动学，不是手调角度

`src/render/walkcycle.ts`，纯 TypeScript，可单测。

核心决定：**每帧只指定脚的位置，膝盖由骨骼长度反解。**

```
solveKnee(hip, target, thigh, shin, bendSign)
```

这让「脚踩在地面上」成为**构造性质**，而不是一个需要反复手调的数字。第一版手调角度时，接触帧的脚落在 y=93.4 而地面在 94——差 0.6px，靠加步长或改髋高去凑，每改一次比例就全盘漂移。改成 IK 后，脚的位置是输入，骨骼永不变形。

比例也改了。原版解剖比例（头 18 / 躯干 26 / 腿 44）在 64×96 上读作「火柴人穿衣服」——64px 宽的画布承载不了支撑写实感所需的细节。改为略 Q 版：

| 部位 | 原 | 现 |
|---|---|---|
| 头 | 18 | 22 |
| 躯干 | 26 | 30 |
| 腿 | 44 | 37（大腿 19 + 小腿 18）|

6 帧循环：接触 → 过渡 → 迈步，后半是前半的换腿镜像。**后半必须是前半的换腿镜像**，否则循环会跛行——一条腿干所有的活。这条不变量有测试守着。

髋高的起伏也是几何逼出来的，不是选的：接触时腿分开所以髋下降（61.7），过渡腿立直所以髋上升（57）。约 3px，是真走路的那一个，不是 B3-12 那个人工 2px。

## 3. 三个我自己犯的错

**① 探针脚本把 8 帧画在同一坐标。** 没有按 `f * FRAME_W` 偏移，所以我第一眼只看到一帧，差点以为只有一帧画出来了。给 `drawPose` 加 `originX` 参数修掉。

**② 测试里自己抄了一份骨骼长度。** `const THIGH = 22; const SHIN = 20;` 和模块里的值脱钩后，测试从模块的新几何重新推导脚踝，算出 y=98.6，报「脚陷到地面下」。代码是对的，是我留了第二份会漂移的常量。改为从模块 `export { THIGH, SHIN }` 并导入。

**③ `solveKnee` 测试两次选了骨骼够不到的目标点。** 然后断言「两块骨头的长度都被满足」，失败。目标是够不到的时候，代码按设计钳制到完全伸展——行为正确，测试选错。已在测试里注明「手工选目标正是这个测试两次栽在这里的原因」。

## 4. 动画接线与防滑步

| 环节 | 做法 |
|---|---|
| 烘焙 | `textures.createCanvas` + `putImageData`，一次调用灌完。用 Graphics + `generateTexture` 需要几万次 `fillRect` 说同一件事 |
| 帧布局 | 每角色一张 512×96 横向表，6 行走帧 + 2 待机帧，`tex.add(f, 0, f*64, 0, 64, 96)` |
| 动画 | `anims.generateFrameNumbers`，行走 8fps 循环，待机 2fps 循环 |
| 朝向 | 侧面图 `flipX` 是正确的——这正是侧面相对正面的优势 |
| **防滑步** | `anims.timeScale = clamp(实际速度 / 最高速度, 0.2, 1)` |

最后一条是本轮最要紧的工程细节：**走路动画按固定帧率播放时，玩家还在加速斜坡上，脚会和地面打滑。** 把播放速率锁到实际速度，脚就不再滑。

## 5. 实测（浏览器）

| 项 | 结果 |
|---|---|
| 烘焙 | 4 张表，各 512×96、8 帧 |
| 动画注册 | 8 个（walk/idle × 4 角色） |
| 切换 | 移动 → `walk-player`，松键 → `idle-player` |
| 帧循环 | `0→1→2→3→4→5` 重复 4 轮（180 帧 @60fps，timeScale=1） |
| 待机循环 | `6↔7` 呼吸 |
| 速度耦合 | 停止后 timeScale=0.2，动画自动放慢到 1/5——打滑不会发生 |
| 镜像 | 向左走 `flipX` 全程为 true |
| 地面 | `player.y` 恒定 320，人工 bob 已移除，垂直运动全部由姿势自带髋高承担 |
| page error | 无 |

## 7. 环境限制（未解决）

**这台机器的 Browser 面板画布上屏只有约 1.2–1.5 fps**，逻辑跑满 60。四组实验定位到成本在画布合成而不在逻辑（循环睡着 rAF 满 60、`display:none` 满 60、Menu 场景单独也 2.8fps、WebGL 是真实 AMD 780M 不是软件回退）。

后果：**我无法在正常帧率下目视确认走路手感。** 所有动画结论都是用定步长驱动循环逐帧采样得到的——数据确定可复现，但「看起来像不像在走」只有你在正常帧率下能判。

## 8. 遗留

| 项 | 状态 |
|---|---|
| 正常帧率下的目视确认 | 未做，只有你能做 |
| 巡游体移动 | 仍是阶跃速度，未套斜坡 |
| 正面渲染图 | 已从世界精灵撤下，但对话立绘尚未接入——目前仍被 BootScene 加载但没有对象使用它 |
| 侧面角色细节 | 程序化像素，细节少于你的渲染图；要替换随时可以，动画与帧表接口不变 |
| 影子 | 角色脚下没有落地阴影，接地感还能再补 |
